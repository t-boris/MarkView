# Task 6: WebViewBridge insight messages and EditorView routing

## Required Skills

## Description

Связать слой `InsightSession` (Task 4) с WebView-плеером режима `insight` (Task 5). Задача состоит из трёх частей:

1. **Swift→JS команды.** Добавить в `WebViewBridge` пять новых методов, которые формируют JS-вызовы и безопасно энкодят payload-строки (markdown, текст delta, заголовки тем, сообщения об ошибках) в JavaScript. Каждый метод соответствует одной из операций инсайт-сессии (полная загрузка снимка, потоковое добавление, обновление списка deep-dive, индикация загрузки, отображение ошибки с флагом retryable).
2. **JS→Swift сообщения.** Добавить в диспетчер `WebViewBridge` пять новых типов сообщений, которые приходят из HTML-режима insight (клик по deep-dive, save, breadcrumb, кнопка up, retry). Каждый тип расширяет `WebViewBridgeDelegate` новым методом, который реализует `EditorView.Coordinator` (а оттуда сообщения уходят в `WorkspaceManager` — Task 7 разведёт их к конкретной сессии).
3. **Маршрутизация в EditorView.** В `loadContentIfNeeded` добавить ветку по `tab.kind`: для `.file` — текущий путь без изменений, для `.insight(session)` — вызов нового `bridge.loadInsightView(snapshot: session.snapshot(), into: webView)` и подписка на `session.$streamingBuffer` / `session.$lastError` через Combine, чтобы каждое обновление буфера форвардилось в JS как `appendInsightDelta`, а ошибка — как `setInsightError`.

Все строковые payload-ы (markdown, deltaText, заголовки тем, сообщения об ошибках) проходят через тот же приём кодирования, что и существующий `loadContent` (L198-217): JSON-сериализация одноэлементного массива и сброс внешних квадратных скобок. Это гарантирует корректный escape кавычек/переводов строк/юникода и предотвращает `NSInvalidArgumentException` при `JSONSerialization.data(withJSONObject:)`.

После форварда обновить `lastForwardedLength = newBuffer.count`. Хранить `lastForwardedLength` в координаторе.

         2. **Затем** вызвать `bridge.loadInsightView(snapshot: session.snapshot(), into: webView)` (полный repaint).
         Используйте `Combine` ordering: подписку на `$currentNodeId` оформлять с `.receive(on: DispatchQueue.main)` и в её sink-блоке выполнять оба шага атомарно перед тем как Combine успеет вызвать $streamingBuffer subscriber.
       - Подписаться на `session.$lastError.compactMap { $0 }.sink { ... }` — вызывать `bridge.setInsightError(sessionId:, message: lastError, retryable: session.lastErrorRetryable, into: webView)`. **ВАЖНО:** не хардкодить `retryable: true` — Task 4 публикует `@Published var lastErrorRetryable: Bool` который зависит от типа ошибки (parseError/noAPIKey/4xx-non-retryable → false; streamingError/5xx/429 → true). Игнорирование флага приведёт к показу Retry-кнопки на нерекаверабельных ошибках (например, неверный API-ключ).
       - Все sink-замыкания используют `[weak self]`.
   - `return` для `.insight` — ветка стандартного markdown loading не должна выполняться.

8. Реализовать в `Coordinator` (extension `WebViewBridgeDelegate`) пять новых методов-форвардеров. ### Edge cases

- **Sessionid в одинарных кавычках:** `UUID().uuidString` всегда соответствует regex `[0-9A-F-]+` — безопасно для одинарных кавычек, но для единообразия с остальными аргументами обернуть через array-wrap.
- **Большой буфер delta:** если `streamingBuffer` обновился сильно (например, переход на новый node — `streamingBuffer = ""` сбрасывает) — `lastForwardedBufferLength` нужно сбрасывать в 0 при смене сессии.
- **Reset буфера на same session:** `InsightSession.expand` или `retryCurrent` могут обнулить `streamingBuffer`. Координатор должен это детектить (если `newBuffer.count < lastForwardedBufferLength` → сбрасываем счётчик и форвардим весь новый буфер). Альтернативно: `InsightSession` может публиковать прямо delta через отдельный `PassthroughSubject<String, Never>` — но это меняет интерфейс Task 4. На этом этапе используем reset-detection.
- **Tab закрыт во время стрима:** `Coordinator` живёт пока живёт `EditorView`, но вкладка может быть закрыта. После закрытия `WorkspaceManager.openTabs[activeTabIndex]` уже не та сессия — `updateNSView` вызовется с другой вкладкой, switch `.file`/`.insight` решит, нужно ли снимать подписки. Сама `InsightSession` будет освобождена через `closeTab` (Task 7) — Combine-подписка на освобождённую сессию не страшна, поскольку `[weak self]` исключает retain cycle.
- **Двойной вызов `loadContentIfNeeded` для той же сессии:** проверка `currentInsightSessionId == session.id.uuidString` — early return, чтобы не пересоздавать подписку при каждом `updateNSView`.
- **Theme switch во время insight:** `setTheme` идёт независимо в `updateNSView` — никакого пересечения с insight-логикой нет.

### Implementation hints

- Encoding-helper можно вынести в приватный метод, чтобы не дублировать array-wrap код пять раз: `private func encodeStringForJS(_ s: String) -> String?` возвращает строку с уже наложенным escape (например `"escaped \\\"text\\\""`).
- Для словарей и массивов (snapshot, topics) можно использовать обычный `JSONEncoder` поверх `Codable`-типов из Task 4. Достаточно `String(data: try encoder.encode(snapshot), encoding: .utf8)`.
- Подписка на Combine: использовать `.receive(on: DispatchQueue.main)` если `InsightSession` публикует не на main (Task 4 предписывает `@MainActor`, поэтому redundant, но безопасно).
- Вместо ручного diff'а буфера можно (Decision 11 совместимо) добавить в `InsightSession` отдельный `@Published private(set) var lastDelta: String = ""` — но это меняет интерфейс Task 4. Альтернатива: ловить полный буфер и считать delta по длине. Выбираем второй вариант для минимального воздействия на Task 4.
- `WebViewBridgeDelegate` существующие методы НЕ менять — только добавлять новые. Все существующие conformer'ы (только `EditorView.Coordinator`) обязаны реализовать новые методы — иначе compile error укажет на места, требующие правки.
