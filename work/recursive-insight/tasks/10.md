# Task 10: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [skills/security-auditor/SKILL.md](~/.claude/skills/security-auditor/SKILL.md)

## Description

Полный security-аудит фичи Recursive Insight. Аудитор проверяет, что **все слои защиты из Decision 10 (и связанных §) реально доехали в код**, а не остались только в спеке. Это финальный security gate перед pre-deploy QA.

Контекст угроз — Decision 10:
- Sandbox в MarkView OFF, WebView-bridge экспонирует save/file actions. Успешный XSS в insight-pane может вызвать `insightSaveRequested` и перезаписать произвольные файлы через NSSavePanel.
- `.md` файлы потенциально untrusted (per user-spec) → prompt-injection риск.
- LLM-генерируемый markdown / Mermaid / scope_hint — всё это атакоспособная поверхность.
- Стрим-pipeline + retry → risk of token-cost runaway, unbounded buffer DoS, leaking API key через ошибки.

Аудит — это **review, а не reviewers**. У этого таска нет ревьюверов: аудитор сам и есть финальный security-голос. Аудитор не пишет код, не модифицирует фичу — только читает все артефакты Tasks 1–8 и пишет отчёт.

Отчёт идёт в `logs/audit/security-audit.md`. Формат отчёта:
- Per-check секция (по одному на каждый из 9 пунктов чек-листа ниже).
- Каждая секция: статус (PASS / FAIL / N/A с обоснованием), файл/линия конкретного места в коде, цитата кода, объяснение почему PASS/FAIL.
- Финальная сводка: список FAIL-пунктов с severity (critical / high / medium / low) и предлагаемое действие (фикс перед merge / acceptable risk / требует решения user).

## What to do

Прочитать все source-файлы, изменённые / созданные в Tasks 1–8 (см. Context Files), и для каждого из 9 пунктов чек-листа Decision 10 вынести вердикт с конкретной ссылкой на код:

1. **markdown-it sanitization (Decision 10 §1).** В `index.html` insight-mode секции — `markdown-it` инициализирован с `html: false`. Link target sanitization: разрешены только `http://`, `https://`, относительные пути. Отвергаются `javascript:`, `data:`, `file:`. Найти конкретное место инициализации, процитировать опции, проверить link-validator.

2. **`Element.textContent` для всех LLM-derived строк (Decision 10 §2).** В insight-mode JS прогнать grep по: `innerHTML`, `outerHTML`, `document.write`, `insertAdjacentHTML`, `Function(`, `eval(`. Любое использование на LLM-derived data (deep-dive labels, hints, breadcrumb titles, error messages, scope_hint paths) — это FAIL. Проверить, что есть единая утилита-обёртка (типа `setText(el, str)`) и что она реально используется во всех местах рендеринга LLM-output. CSP в текущем проекте оставляет `script-src 'unsafe-inline'` (compat с другими режимами — Decision 10 §3), поэтому JS-side hygiene — главный барьер от script injection.

3. **CSP meta tag (Decision 10 §3).** В insight-mode HTML контейнере (или в `<head>` секции index.html, активной для insight-mode) присутствует `<meta http-equiv="Content-Security-Policy" content="...">` со всеми требуемыми директивами:
   - `default-src 'self'`
   - `script-src 'self' 'unsafe-inline'`
   - `style-src 'self' 'unsafe-inline'`
   - `connect-src 'none'` (критично — блокирует exfil через `<img>`/fetch)
   - `img-src 'self' data:`
   - `object-src 'none'`
   - `base-uri 'none'`
   Процитировать meta tag, отметить любые отклонения.

4. **Mermaid `securityLevel: 'strict'` per-render (Decision 10 §4).** В insight-mode рендере Mermaid каждый блок инициализируется с `securityLevel: 'strict'`. Проверить, что это **per-render**, а не глобально (per Decision 7 — глобальная инициализация остаётся, но insight-mode перепроставляет strict). Найти место в `index.html`, процитировать.

5. **System prompt isolation (Decision 10 §5).** В `GraphRAG.mapReduceForFolder` и в `InsightSession` (методы `generateRoot`, `expand`) — system prompts оборачивают `.md`-контент в XML-теги (`<file path="...">...</file>`) с явной инструкцией модели treat-as-data. Проверить шаблон промпта в обоих файлах, процитировать. Для root-пути ≤30 файлов (single `streamCompletion` напрямую из `InsightSession`) — отдельная проверка.

6. **`scope_hint` validation (Decision 10 §6).** В `InsightSession` каждый путь из `scope_hint`, возвращённый LLM, валидируется через `URL(fileURLWithPath:relativeTo: folderURL).resolvingSymlinksInPath().standardizedFileURL` с проверкой containment против `folderURL.resolvingSymlinksInPath().standardizedFileURL.path`. **Критично:** `.resolvingSymlinksInPath()` идёт ПЕРЕД `.standardizedFileURL` (иначе symlink, указывающий за пределы папки, пройдёт проверку). Дополнительно отвергаются файлы с расширением != `.md`. Failed paths — log + skip, не raise. Найти и процитировать validator. Аналогично — в `WorkspaceManager.scanMarkdownFiles` проверить `.skipsPackageDescendants` и symlink-containment.

7. **Resource caps (Decision 10 §7 + Decision 5).** Проверить enforcement каждого:
   - 50 KB на файл (truncation в `GraphRAG.mapReduceForFolder` и в single-file path `InsightSession`)
   - 500 файлов на папку (hard cap в `WorkspaceManager.scanMarkdownFiles` или `startRecursiveInsight`)
   - 200 KB per-community (subdivision в `GraphRAG.mapReduceForFolder`)
   - 10 MB на `InsightNode.rawBuffer` (cap в `InsightSession`, on exceed → cancel + `.failed`)
   - 50 MB на `InsightSession` total (eviction oldest non-current path nodes)
   - 64 KB на SSE line (`AIProviderClient.streamCompletion`)
   - Retry throttle: 3 retries / 60s sliding window per node (`InsightSession.retryCurrent`)
   Для каждого capа: процитировать константу + место enforcement.

8. **API key never leaks (Decision 11 + Task 1 invariant).** Grep по всем модифицированным `.swift` файлам на:
   - `apiKey` в `String(describing:)`, в `NSLog`, в `print`, в `throw` сообщениях
   - В `AIProviderClient.streamCompletion`: проверить sanitize-helper и его применение во всех throw-ветках (HTTP error, parse error, line-too-long, error-event)
   - В `InsightSession.handleStreamError`: проверить, что `lastError` не содержит ключ
   - В bridge messages: `setInsightError(message:)` не содержит ключ
   Процитировать sanitize-функцию, её call-sites.

9. **NSSavePanel sanitization (Task 7 + Decision 10).** В `WorkspaceManager` save-handler:
   - Default filename derived from `currentNode.title` санитизирован (alphanumeric + underscores only)
   - Расширение `.md` форсируется (даже если user удалил/изменил)
   - Проверить, что нет path-traversal через имя файла (NSSavePanel сам нормализует, но удостовериться что мы не делаем странных манипуляций до)
   Процитировать sanitization.

После всех 9 проверок написать сводный отчёт:
- Список всех FAIL с severity
- Список passed-with-warnings (что-то технически корректно, но fragile)
- Финальный verdict: SAFE TO MERGE / FIXES REQUIRED / NEEDS USER DECISION

## Verification Steps

### Automated

Аудит сам по себе является verification — отдельных автоматических тестов нет. Аудитор должен явно выполнить и задокументировать в отчёте следующие grep-команды (это часть процесса аудита, не отдельный шаг):

- `grep -nE "innerHTML|outerHTML|document\.write|insertAdjacentHTML|Function\(|eval\(" MarkView/Resources/Editor/index.html` — для каждого хита: где и применяется ли к LLM-derived data?
- `grep -nE "apiKey|api_key" MarkView/Models/*.swift` — для каждого хита в throw/NSLog/print: проходит ли через sanitize?
- `grep -n "securityLevel" MarkView/Resources/Editor/index.html` — есть ли `'strict'` в insight-mode?
- `grep -n "Content-Security-Policy" MarkView/Resources/Editor/index.html` — присутствует ли CSP, какие директивы?
- `grep -n "resolvingSymlinksInPath\|standardizedFileURL" MarkView/Models/*.swift` — порядок вызовов?

### Smoke

Не применимо — аудит читает код, ничего не запускает. Если аудитор хочет ручную проверку CSP в работающем приложении — это уже входит в pre-deploy QA (Task 12, Instruments + manual flow).

**Dependencies:** все задачи 1–8 должны быть в статусе `done`. Если какая-то ещё `in_progress` или `failed` — аудитор отмечает это в отчёте и аудирует только что есть, а недостающие части помечает как N/A с пояснением.

**Edge cases:**
- **Файл, упомянутый в Context Files, не существует** (например, `InsightSession.swift` не создан, потому что Task 4 не завершён) → отметить в отчёте, проверки касающиеся этого файла → N/A с пояснением.
- **Тулинг grep падает на бинарных файлах** — использовать `--include='*.swift'`, `--include='*.html'` для безопасности.
- **`unsafe-inline` в CSP** — это compromise, не FAIL. Decision 10 §3 явно retains `script-src 'unsafe-inline'` для compat с другими режимами. Отметить в отчёте как known limitation, mitigation — JS-side hygiene из §2.
- **`scope_hint` = пустой массив** — валидно (deep-dive без явных файлов). Validator должен это корректно обрабатывать.
- **Файл существует, но содержит TODO/FIXME относящиеся к security** — отметить как warning, не FAIL, в сводке.

**Implementation hints:**
- Структура отчёта (предлагаемый шаблон, не обязательный):
  ```
  # Security Audit Report — Recursive Insight

  ## Summary
  Verdict: SAFE TO MERGE | FIXES REQUIRED | NEEDS USER DECISION
  Critical: N | High: N | Medium: N | Low: N

  ## Check 1: markdown-it sanitization (Decision 10 §1)
  Status: PASS | FAIL | N/A
  Location: file.ext:LINE
  Evidence:
  ```code snippet```
  Notes: ...

  ## Check 2: ...
  ...

  ## Findings (FAILs only)
  ### F1 (severity: critical)
  Check: N
  Issue: ...
  Suggested fix: ...
  Action: blocks merge / non-blocking / needs user decision
  ```
- Severity guideline:
  - **critical** — exploitable XSS, RCE, path traversal, key leak
  - **high** — bypass возможен с realistic input (например, LLM-induced)
  - **medium** — defense-in-depth слой отсутствует, но другие слои спасают
  - **low** — стилистика, missing logging, fragile pattern без активной угрозы
- Если несколько проверок находят один корневой баг (например, забытый `setText` приводит к multiple FAIL) — указать кросс-ссылки, чтобы фиксер не делал двойную работу.
- Для проверки 8 (API key) — использовать grep с regex, потом руками верифицировать каждый хит, потому что false positives возможны (например, `apiKey` как параметр функции — не leak сам по себе, leak только если попадает в throw/log).
