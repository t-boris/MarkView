# Task 9: Code Audit

## Required Skills

## Description

Полнофичевый code-quality аудит фичи Recursive Insight. Этот таск запускается после того как Wave 1-3 (Tasks 1-8) полностью реализованы и закоммичены — он смотрит на feature целиком (а не отдельные диффы), потому что многие свойства (правильность shared resources, корректность propagation ошибок через async-границы, lifecycle стримов) видны только в межфайловой композиции.

**Почему именно этот аудит критичен для этой фичи:**

1. **Первый streaming code path в кодовой базе.** До Recursive Insight в MarkView не было ни одного `URLSession.bytes(for:)` вызова, ни одного SSE-парсера, ни одного long-lived `Task` который писал бы в `@Published` state поверх async-границы. Это значит — нет прецедента, нет уже существующих паттернов в проекте, которые можно было бы скопировать. Аудитор первым проверяет, что новый код не закладывает антипаттернов на будущее.

2. **`[weak self]` mandate из Decision 11 §1.** Каждое замыкание, захваченное `Task`, `URLSession.bytes` итератором, или передаваемое как `onDelta` callback в `streamCompletion`, ОБЯЗАНО капчевать `self` через `[weak self]`. Strong-capture в long-lived async — задокументированный путь к retain-cycle, а в этой фиче таких мест много (особенно в `InsightSession.generateRoot`, `expand`, `retryCurrent`, `handleStreamError`). Аудитор должен пройтись grep-ом и глазами по каждому такому месту и **явно зафлажить любой strong-capture `self`**.

3. **Shared resources (`AIProviderClient`, `GraphRAG`).** Tech-spec определяет: один экземпляр `AIProviderClient` на весь workspace, переиспользуется через `incrementalCompiler.orchestrator.providerClient`. Аналогично один `GraphRAG`. Если кто-то по ошибке создал новый `AIProviderClient()` внутри `InsightSession.init` — мы потеряли cache API key, потеряли единую точку настройки, удвоили память. Аудитор обязан верифицировать grep `AIProviderClient(` по всему фиче-диффу и убедиться что единственное место создания — то самое, что было до фичи.

4. **Tests deferred (Decision 9).** Поскольку automated test suite для этой фичи отсутствует, hand-trace SSE-парсера против fixture (`Tests/Fixtures/sse-anthropic-sample.txt`) и marker-парсера против fixtures (`Tests/Fixtures/marker-cases/*.md`) — это compensating verification. Аудитор фактически выполняет работу, которую сделал бы test runner: подаёт fixture на вход парсеру в голове, проверяет что выход совпадает с задокументированным ожиданием.

5. **Multiple language boundaries.** Фича пересекает Swift ↔ JS bridge (5 Swift→JS команд, 5 JS→Swift сообщений), и Swift async ↔ SwiftUI `@Published`. Каждая граница это потенциальный источник encoding-bug, threading-bug, или dropped-message. Аудитор смотрит на консистентность encoding (array-wrap idiom для evaluateJavaScript), на `@MainActor` annotations в правильных местах, на отсутствие гонок при tab-switch.

**Audit task НЕ пишет код.** Единственный output — markdown-отчёт `logs/audit/code-audit.md` с findings, severity, recommendations. Если найдены критические проблемы — они становятся feedback'ом для повторной реализации соответствующих тасков (через mode=fix), но это уже не в скоупе этого audit-таска.

**Auditor IS the review.** Этот таск не имеет своих reviewers (`reviewers: []` в frontmatter) — сам аудитор и есть review-слой над Implementation Tasks 1-8. Если аудит сам по себе содержит ошибки — это ловится только в Wave 5 (Pre-deploy QA, Task 12) когда сверяются acceptance criteria.

1. **Прочитать всё, что было создано/модифицировано Tasks 1-8.** Список файлов в секции Context Files. Читать целиком — не выборочно. Цель: построить mental model связности фичи (кто кого вызывает, кто чем владеет, кто что отменяет).

2. **Проверить shared resources compliance.**
   - `grep -rn "AIProviderClient(" MarkView/Models/InsightSession.swift MarkView/Models/GraphRAG.swift MarkView/Models/WorkspaceManager.swift` — должно показать ноль новых конструкторов. Все consumers должны получать инстанс через DI (через `init(providerClient:)`) или через `incrementalCompiler.orchestrator.providerClient`.
   - Аналогично для `GraphRAG`.
   - Зафиксировать в отчёте: instance count по таблице shared resources из tech-spec соответствует фактическому коду или нет.

3. **`[weak self]` audit (Decision 11 §1) — главный фокус.**
   - Прочитать `InsightSession.swift` целиком, найти ВСЕ места создания замыканий, которые передаются в `Task { ... }`, `URLSession.bytes` или передаются как `onDelta` callback в `streamCompletion`/`mapReduceForFolder`.
   - Для каждого замыкания проверить: первая строка должна содержать `[weak self]` capture. Если `[weak self]` отсутствует — это **критическая** находка (severity: critical).
   - Также проверить: после `[weak self]` capture идёт `guard let self = self else { return }` или `self?.foo` pattern. Если идёт `self.foo` без unwrap — это либо не работает (compile error), либо в реальности `self` всё ещё strong (опечатка в capture list) — флажить.
   - В тот же чек: `WorkspaceManager.startRecursiveInsight()` в Task 7 — `Task { await session.generateRoot() }` тоже должен быть `Task { [weak session] in ... }` или эквивалент, потому что он живёт за пределами scope метода.

4. **Task cancellation корректность.**
   - Проверить что `InsightSession.cancel()` вызывает `activeTask?.cancel()` И затем `activeTask = nil`. Один без другого — ошибка.
   - Проверить что `expand()` и `retryCurrent()` отменяют предыдущий `activeTask` ДО старта нового (иначе race: два стрима пишут в один `streamingBuffer`).
   - Проверить что внутри SSE-парсера `streamCompletion` есть `try Task.checkCancellation()` между обработкой линий — иначе `cancel()` не остановит стрим в течение 1 секунды как требует acceptance criterion.
   - Проверить порядок в `closeTab(at:)`: `session.cancel()` ДО `tabsStore.removeTab(at:)`. Если наоборот — есть окно, в котором `Task` всё ещё пишет в session, на которую больше никто не держит strong reference (хотя тут ARC спасает, но порядок предписан Decision 11 §4 явно).

5. **Error propagation через async boundaries.**
   - Любое `throws` в `streamCompletion` должно либо пробрасываться наружу, либо быть пойманным в `do/catch` с конкретным `AIProviderError` case (не голый `Error`, не silent swallow).
   - `InsightSession.handleStreamError` должен: установить `currentNode.status = .failed`, заполнить `lastError`, оставить `rawBuffer` НЕТРОНУТЫМ (preserve partial), вызвать bridge `setInsightError(retryable: true)`.
   - Никакой `catch { }` без обработки. Никакой `try?` который проглатывает ошибку молча в критических местах (стрим, save).

6. **Swift/AppKit conventions.**
   - `@MainActor` на `InsightSession` (т.к. она пишет в `@Published` properties, которые drives SwiftUI).
   - `@Published` properties помечены `private(set)` — мутация только изнутри класса.
   - Нет force-unwrap (`!`) на user-derived data, на parsed JSON, на URL'ах из LLM scope_hint.
   - `URL` манипуляции — через `URL` API, не string concat.
   - File I/O в `WorkspaceManager.startRecursiveInsight`/save handler — на `DispatchQueue.global` или в `Task.detached`, не на main.
   - Соблюдение существующих именований (camelCase, что-то типа `tabsStore.appendTab(_:)`).

7. **JS code quality (`MarkView/Resources/Editor/index.html`).**
   - Insight-mode код должен жить рядом с другими mode-handler'ами, использовать тот же `state` object.
   - `markdown-it` инициализирован с `html: false` — критично, иначе LLM может инжектить `<script>`.
   - Все LLM-derived строки (deep-dive labels, hints, breadcrumb titles, error messages) пишутся через `Element.textContent`, никогда `innerHTML`. Утилита `setText(el, str)` используется во ВСЕХ местах — grep по `innerHTML` в insight-mode коде должен дать ноль hits на LLM-derived строки.
   - CSP meta tag присутствует с директивами как в Decision 10 §3.
   - Mermaid вызывается с `securityLevel: 'strict'` per-render.
   - Per-block try/catch вокруг `mermaid.run` — один bad block не должен ломать весь стрим.
   - Debounce render (~150ms) реализован — иначе jank на быстрых стримах.
   - Marker parser: ищет последнее вхождение `\n\n---DEEP-DIVES---\n` (обе стороны boundary newlines), не реагирует на bare `---`.

8. **Theme compatibility.**
   - Insight-mode UI использует CSS-переменные темы (например `--bg`, `--fg`, `--border`), а не hardcoded `#fff` / `#000`.
   - Split-pane корректно отображается в light и dark теме (если в проекте есть тестовые темы).
   - Error banner, deep-dive list, breadcrumbs — все элементы респектят theme.

9. **Hand-trace SSE parser против `Tests/Fixtures/sse-anthropic-sample.txt`.**
   - Прочитать fixture целиком.
   - Подать его в голове в parser `AIProviderClient.streamCompletion`. Для каждой линии — определить: какая ветка обработает (event/data/comment/empty), что получится в `onDelta` callback'ах.
   - В отчёте: список всех ожидаемых `onDelta` вызовов в порядке их возникновения, с пометкой "матчит ли реализацию".
   - Если в fixture есть oversized line (>64KB) — должен сработать `streamingError` early. Если есть `event: error` — должен throw. Если есть `: ping` keepalive — должен молча пропустить.

10. **Hand-trace marker parser против `Tests/Fixtures/marker-cases/*.md`.**
    - 5 fixture-файлов: `happy.md`, `in-code-fence.md`, `as-hr.md`, `no-marker.md`, `multiple-markers.md`.
    - Для каждого: определить ожидаемый output (markdown body + список deep-dives) согласно правилам Decision (последнее вхождение, `\n\n` boundaries).
    - Прочитать JS-код парсера в `index.html`, прогнать в голове на каждом fixture, сравнить.
    - Особо: `in-code-fence.md` — marker внутри ``` блока НЕ должен распознаваться (но JS парсер работает на raw text без понимания markdown синтаксиса — поэтому либо парсер ищет marker ДО рендера и пропускает (тогда ловится случайно), либо игнорирует контекст fence — задокументировать поведение).
    - `as-hr.md` — bare `---` без префикса `\n\n---DEEP-DIVES---\n` не должен матчиться.
    - `multiple-markers.md` — должен взять только последнее вхождение.

11. **Написать audit report.** Файл `logs/audit/code-audit.md`. Структура:

- Если auditor находит ошибку в самом tech-spec (например, противоречие между Decision 10 §6 и реальной возможностью валидации scope_hint) — флажить отдельной категорией `[spec-issue]`, не как code finding.
- Если какой-то участок кода не покрыт ни одним требованием спека, но выглядит подозрительно — флажить как `[info]` с описанием.

**Implementation hints (для самого аудитора):**
- Использовать `grep -rn "pattern" file.swift` для систематического поиска (например `grep -rn "\[weak self\]" MarkView/Models/InsightSession.swift` и сравнить с `grep -rn "Task {" MarkView/Models/InsightSession.swift`).
- Для hand-trace SSE: распечатать (mentally) каждую линию fixture, рядом написать что произойдёт в parser. Полный дамп — в отчёт.
- Для hand-trace marker: каждый из 5 fixture-файлов прогнать через JS-парсер в голове, документировать input → expected output → actual (как ведёт себя код).
- Не дублировать работу security-auditor (Task 10) и test-master (Task 11) — фокус именно на code quality, конвенциях, lifecycle, async-корректности. Security-specific (CSP, sanitize, scope_hint validation) аудитор тоже проверяет, но как часть общего code review, не как отдельный security pass.
- Severity calibration: `critical` = блокирует merge (data loss, retain cycle, key leak). `major` = исправить до merge (неправильная error propagation, missing `[weak self]`, broken cancellation). `minor` = после merge ОК (naming, comments, micro-optim). `info` = наблюдение, не действие.
