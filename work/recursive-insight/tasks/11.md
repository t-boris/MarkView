# Task 11: Test Audit (v2-specific re-derivation)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:test-master` — [skills/test-master/SKILL.md](~/.claude/skills/test-master/SKILL.md)

## Description

Meta-audit of the Recursive Insight v2 testing posture. Tests are still deferred per Decision 9 (no XCTest target exists in MarkView), so this audit's job is NOT to write tests — it is to prove that the deferral is honest, that the follow-up `tasks/todo.md` accurately reflects what we owe ourselves, and that no v2 risk class smuggles itself past the deferral by being plausibly testable today.

The auditor must **re-derive** required test coverage directly from v2 architecture (skeleton + iframe sandbox + InsightCache + ZIP export + blob URLs + parallelism cap + iframe load timeout + CSP). Do NOT analogize from v1's deferred test list — v2 introduces 4 new risk classes (sandbox boundary, atomic write, ZIP path safety, parallel cap) that v1 did not have, and v2 deletes v1 surfaces (the `---DEEP-DIVES---` marker parser, the right-pane deep-dive list, v1 SSE parser specifics) so v1 test names like `InsightMarkerParserTests` are now meaningless and must not appear in the rewritten follow-up.

The audit cross-references the Code Audit (T9) and Security Audit (T10) outputs to identify any path that those reviewers flagged as "should have a test before merge" despite the broader deferral, and surfaces those as exceptions that need pre-merge XCTest infrastructure or explicit risk-acceptance.

It also validates that T12 Pre-deploy QA's 12 Instruments scenarios (5 happy-path + 7 adversarial per tech-spec line 737) provide adequate runtime coverage for the new ARC surfaces (InsightCache lifetime, InsightArchiveExporter Process lifetime, iframe blob URL lifecycle across navigation, multi-session sequencing if user opens/closes several insight tabs in succession).

The output is a single report at `logs/audit/test-audit.md`.

3. Read the rewritten `tasks/todo.md` (post-T8). Confirm:
   - All v1-only deferred test modules are REMOVED. Specifically: `InsightMarkerParserTests`, `InsightSSEParserTests` if it referenced v1 marker semantics, any test name implying right-pane deep-dive list, any `setInsightDeepDives` test, any `appendInsightDelta` v1-bridge test.
   - All 8 v2 deferred test areas are PRESENT and described concretely:
     1. Anthropic `tool_use` parsing — happy path, missing tool_use block, malformed `input`, schema validation fallback to single-prose-section InsightSkeleton.
     2. postMessage allowlist + payload schemas + `frameInfo.isMainFrame` defense + parent JS `event.source === iframe.contentWindow && event.origin === 'null'` validation. Includes: rejection of non-allowlisted message types; rejection of malformed payloads; topicIndex bounds check on `insightDeepDiveClicked`; nodeId UUID + manifest membership check on `insightBreadcrumbClicked`.

Includes: deep-dive onclick rewriting from postMessage to `window.location.href`; lib `<script src="blob:...">` rewriting to `<script src="_assets/<lib>.js">` (root) and `../_assets/<lib>.js` (nodes/); breadcrumb href rewriting; escape utility applied at every interpolation site.

5. Verify Pre-deploy QA (T12) Instruments leak-check scenarios cover the new ARC surfaces. Tech-spec line 737 enumerates 12 scenarios `(a)` through `(l)`. Map each new ARC surface to at least one scenario:

6. Note any risk row that has neither code mitigation nor QA scenario nor deferred test — those are gaps.
7. Write `logs/audit/test-audit.md` with the structure described in the Details section. Findings must be evidence-cited: every claim links to a tech-spec line range, an audit report finding id, or a `tasks/todo.md` line.

**Edge cases:**

- Code Audit or Security Audit raises a finding that recommends a test BEFORE merge — auditor must NOT silently file it under "deferred"; must surface it as a "Pre-merge exception" requiring test infra setup or explicit risk-acceptance from the user.
- `tasks/todo.md` post-T8 still contains a v1-only test name — auditor must flag as a regression in T8 (test-master can recommend an Edit; do not silently ignore).
- A v2 risk row in tech-spec has no code mitigation, no QA scenario, no deferred test — coverage gap. Auditor lists it.
- Decision 9 itself becomes untenable (e.g. Code Audit finds 3+ paths recommending pre-merge tests) — auditor recommends NO-GO. The user can either set up test infra or explicitly accept the risk; the audit's job is only to surface this honestly.
- A QA scenario in T12 references behavior that was changed in T1–T8 (e.g. an old bridge method name) — auditor flags T12 as needing an Edit before execution.

**Implementation hints:**

- Use the v2 acceptance criteria (tech-spec lines 554-644) as the master checklist — every criterion either has a code-side enforcement (verified by Code/Security Audit) or a deferred test (verified by `tasks/todo.md` cross-check). Walk both directions: from criterion to coverage, and from `tasks/todo.md` entry back to a criterion. Both walks must land — orphaned entries in either direction are a finding.
- The 8 deferred areas come straight from tech-spec Decision 9 "Critical paths to add to follow-up scope" (lines 273-280) plus the additional T8 rewrite scope listed in tech-spec line 711. Do not invent extra areas; do not omit listed ones.
- For test naming, follow the v1 style observed in `tasks/todo.md` (e.g. `Tests/InsightSSEParserTests.swift`, `Tests/InsightCancellationRaceTests.swift`). The names suggested by this audit are aspirational — they will be implemented when XCTest infra arrives, but a clear name now removes ambiguity later.
- Cite tech-spec lines like `tech-spec.md:584` (CSP line) — short and unambiguous. For audit-report findings, use the report's own finding ids (e.g. `code-audit.md#F-12`).
- Do not propose new tests for v1-only modules. The marker parser, the right-pane deep-dive list, the v1 5 bridge methods, and the v1 SSE marker semantics are GONE in v2 (per tech-spec lines 55-61); deferred tests for them would be dead code-by-definition.
- Re-derivation discipline: when describing a deferred test, state WHY it's needed in v2 architecture terms (e.g. "Phase 2 uses `withThrowingTaskGroup` capped at 5; without a test, regressions to the cap are silent — a future contributor could change `5` to `unlimited` and no build error would surface"). Don't say "v1 had this so v2 needs it".

**Audit invariants:**

- Every claim cites either a tech-spec line, an audit finding id, or a `tasks/todo.md` line.
- The GO / NO-GO recommendation appears in both Summary and Recommendation sections — do not bury it.
- The report does not propose to write any tests in this PR (the deferral stands per Decision 9). Its job is to audit posture, not to retroactively close the gap.
- The report flags ANY v1-only artifact still referenced anywhere in v2 deferred tests — those are stale by definition.
