## Description

This is the Wave 5 integration task that wires the v2 InsightSession (T6) and v2 WebViewBridge (T7) into `WorkspaceManager` — the singleton that owns the tab store, all 5 bridge delegate forwarders for insight, the `closeTab` insight branch, and the 9 insight-tab disk-write guards inherited unchanged from v1 (commit `aaee220`). It is the first task that exercises the full v2 pipeline end-to-end from a user-visible action.

Three discrete pieces of work are bundled here because they share the same file (`WorkspaceManager.swift`) and must land atomically — the bridge delegate signatures changed in T7, so the moment T7 ships, `WorkspaceManager`'s old forwarders no longer compile. The pieces are:

1. **Adapt the 5 forwarders** (`didRequestInsightDeepDive`, `didRequestInsightSave`, `didRequestInsightBreadcrumb`, `didRequestInsightUp`, `didRequestInsightRetry`) to the v2 bridge payloads — chiefly `deepDiveClicked` now carries `(sectionId, topicIndex)` (with bounds + manifest validation against the current `InsightSkeleton.sections[sectionId].deepDiveTopics`), `breadcrumbClicked` carries `nodeId` (UUID-regex + manifest membership check), and `requestSave` triggers archive export instead of saving a node body.
2. **Replace the 4-line `closeTab` insight branch** with the EXACT 4-step ordered cleanup from Decision 11 + Architecture › Tab close: (1) `bridge.releaseInsightBlobs(into: webView)` to revoke parent-side blob URLs BEFORE any Combine sub can fire post-revocation, (2) `await session.cancel()` to cancel `activeTask` + all parallel Phase 2 section tasks AND any in-flight ZIP export Process, (3) `try? session.cache.cleanup()` to remove `.insight-cache/<sessionUUID>/` and orphan `.tmp` files, (4) `tabsStore.removeTab(at:)`. Order matters and is a tested race-condition fix; reviewers WILL flag any reordering.
3. **Replace `saveInsightNode(_:fromSession:)` with `exportInsightArchive(sessionId:)`**: NSSavePanel (default `<folderName>_insight_<timestamp>.zip`) → `cache.archiveStagingDirectory()` builds staging dir with deterministically-rebuilt HTML (per Decision 10 escape utility) and lib `_assets/` → `InsightArchiveExporter.bundle(stagingURL:to:)` spawns `/usr/bin/zip` via Foundation `Process` with an explicit argument array (NEVER `/bin/sh -c` — command injection risk because the destination URL is user-chosen and could contain shell metacharacters in filename) → atomic move `.zip.tmp` → final URL on `terminationStatus == 0`. The Process is cancellable: if the user closes the tab during a long export, the in-flight Process is terminated and the staging dir + `.zip.tmp` cleaned.

Two subordinate deliverables:
- **New file `MarkView/Models/InsightArchiveExporter.swift`** — implements `bundle(stagingURL:to:) async throws` using Foundation `Process` exactly as `GitClient.swift:192-206` does (launchPath + arguments + Pipe; await `terminationStatus`; sanitize stderr in error path). Cancellation hook via `Task.checkCancellation` between launch and await; on cancel, send SIGTERM via `process.terminate()`.
- **Rewrite `tasks/todo.md`** to remove v1-only test scope (e.g. `InsightMarkerParserTests` for the deleted marker parser, marker-cases fixture suite) and add the 8 v2 paths enumerated by Decision 9: Anthropic tool_use parsing + skeleton schema + fallback, postMessage allowlist + payload schemas + frameInfo + event.source/origin defense, InsightCache atomic CRUD + manifest, ZIP export staging + HTML rewriting + escape policy, blob URL lifecycle, Phase 2 parallelism cap, iframe srcdoc CSP, iframe load timeout. T11 (Test Audit) re-derives test scope from v2 architecture and verifies this rewrite.

The 9 v1 insight-tab disk-write guards (Cmd+S; saveFile(at:); reloadActiveTabFromDisk; openOrRefreshFile refresh-branch; updateActiveTabContent; reindexActiveFile single-file branch; handleBlocksDelta; EditorView.Coordinator.bridgeSaveRequested; bridgeRefreshRequested) are inherited UNCHANGED — they only check `if case .insight = tab.kind { return }` which is still the correct invariant for v2 (insight content is never saved to user disk via the editor save path; it's exported via the ZIP path). Do NOT touch these guards. Reviewers will diff against `aaee220` to confirm.

- User chooses destination on different volume than staging dir → `FileManager.moveItem` may fail with cross-device error; fall back to `copyItem` + `removeItem` (or use `replaceItemAt` which handles cross-volume).
