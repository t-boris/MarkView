# Task 1: AIProviderClient.toolCall (Anthropic tool_use)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Add a new `toolCall(name:description:inputSchema:systemPrompt:userMessage:model:maxTokens:)` async method to `AIProviderClient` that invokes Anthropic Messages API with the `tools` field and returns the parsed `tool_use` input dict. This is the first **structured-output / strict-schema** code path in the codebase — Phase 1 of the v2 Recursive Insight pipeline depends on it to obtain a schema-validated `InsightSkeleton` JSON before Phase 2 streams individual sections in parallel.

The implementation must reuse the existing `apiKey`, header set (`x-api-key`, `anthropic-version: 2023-06-01`, `content-type: application/json`), `URLSession.shared`, error sanitize helper, and `AIProviderError` cases established by `extractSingleChunk` and `streamCompletion`. It must NOT change anything else in the file — Decision 8 mandates additive change with minimal blast radius (existing AI features such as translation/diagrams/extraction stay untouched).

In the same task, commit a representative sample tool_use response at `Tests/Fixtures/insight-skeleton-sample.json` mirroring the `InsightSkeleton` data model from tech-spec (title, suggestedTheme, sections with id/type/title/scopeHint/metadata/deepDiveTopics). The fixture lets the code-reviewer hand-trace the parser without hitting live API and gives test-reviewer a deferred-tests anchor (per Decision 9).

Per Decision 9 the project still has no XCTest target; intended tests are listed below for the deferred follow-up.

## What to do

1. Add `toolCall(...)` async throws method to `AIProviderClient` with exactly the signature specified in tech-spec Data Models section:
   `func toolCall(name: String, description: String, inputSchema: [String: Any], systemPrompt: String, userMessage: String, model: String = "claude-sonnet-4-6", maxTokens: Int = 8192) async throws -> [String: Any]`
2. Build the Anthropic Messages API request body with: `model`, `max_tokens`, `system`, `messages: [{role: "user", content: userMessage}]`, `tools: [{name, description, input_schema}]`, `tool_choice: {type: "tool", name: <name>}` so the model is forced to call exactly this tool.
3. Reuse the existing request shape from `extractSingleChunk` / `generateMermaidDiagrams`: same headers (`Content-Type`, `x-api-key`, `anthropic-version: 2023-06-01`), `URLSession.shared`, request URL `baseURL`, sensible timeout (180s — matches `extractSingleChunk`).
4. On non-200 HTTP: throw `AIProviderError.httpError(status, sanitize(body))`. Body must go through the existing private `sanitize(_:)` helper so the API key is redacted before the error escapes.
5. On 200: parse JSON, locate the first `content` block whose `type == "tool_use"`, extract its `input` field as `[String: Any]`, return that dict. If no tool_use block found, throw a descriptive error (reuse `parseError` or add a new `toolCallError` case to `AIProviderError` if a tool-specific failure mode is warranted — caller-facing string must NOT contain the API key; route through `sanitize`).
6. Pre-flight: if `apiKey` is nil/empty, throw `AIProviderError.noAPIKey` (mirrors all other public methods).
7. Create `Tests/Fixtures/insight-skeleton-sample.json` containing a realistic full Anthropic Messages response envelope with a `tool_use` block whose `input` matches the `InsightSkeleton` Codable shape from tech-spec Data Models (title, optional suggestedTheme, sections array with at least 3 sections covering different `SectionType` values, including a section with `deepDiveTopics`). The fixture is documentation/hand-trace only — it is committed to the repo, not loaded by code (no XCTest target exists).
8. Verify the new method compiles cleanly (no new warnings) by running `xcodebuild` build before handing off to reviewers.

Optionally add `case toolCallError(String)` to `AIProviderError` if needed; if added, also extend the `errorDescription` switch — sanitize the message before storing it in the case (mirror the comment pattern from `streamingError` line 733-734).

Mirror the full Anthropic Messages API response envelope: top-level `id`, `type: "message"`, `role: "assistant"`, `model: "claude-sonnet-4-6"`, `content: [{type: "tool_use", id: "toolu_xxx", name: "insight_skeleton", input: {...InsightSkeleton...}}]`, `stop_reason: "tool_use"`, `usage: {input_tokens, output_tokens}`. The `input` payload must include realistic values: e.g. `title: "Project Architecture Overview"`, `suggestedTheme: "dark"`, `sections` with one `hero`, one `mermaidDiagram` (with `metadata: {chartType: "graph TD"}`-style hint), one `prose` carrying a `deepDiveTopics` array of two entries.

**Dependencies:**

- None on other tasks — Wave 1 foundation. T4 (GraphRAG v2 prompts) and T6 (InsightSession rewrite) consume `toolCall` later.
- No new SwiftPM packages.

**Edge cases:**

- Anthropic returns 200 but `content` is empty or has no `tool_use` block (model refused / hit safety filter). Handle gracefully — throw a descriptive error, don't crash, don't expose API key.
- Anthropic returns `tool_use` block with malformed `input` (not valid JSON object — extremely rare). `JSONSerialization` already returns `[String: Any]` if it parses; the cast to `[String: Any]` may fail. Throw a descriptive error.
- Anthropic returns multiple content blocks (e.g. one `text` block followed by one `tool_use` block). Implementation must scan ALL blocks for the first `tool_use`, not just `content[0]`.
- HTTP 401 / 403 (bad key). The error body from Anthropic typically includes the offending request snippet — sanitize MUST run before the body is wrapped in `httpError`.
- HTTP 429 (rate limit). Same sanitize discipline; caller (InsightSession) handles retry — T1 just propagates the error.
- Network error / timeout. Throws as a non-`AIProviderError` underlying error from `URLSession`; either wrap in `streamingError`/`parseError` (sanitized) or let it propagate. Pick one consistent with `extractSingleChunk` (which lets URLSession errors propagate raw — that pattern leaks no API key because URLSession errors don't include the request body).
- API key has unusual characters (e.g. spaces accidentally pasted). `sanitize` does literal substring replacement, which is correct.

**Implementation hints:**

- Closest reference is `generateMermaidDiagrams` (lines 568-660): already builds a `tools` array with `input_schema`, sets `tool_choice`, parses `tool_use` from the response. Use the same shape; the new method is more generic (caller supplies `name`, `description`, `inputSchema` instead of hardcoded values).
- Use `tool_choice: {type: "tool", name: <name>}` to force the model to invoke this specific tool (don't leave it free to emit text instead — that breaks the structured-output guarantee Decision 1 relies on).
- Defer schema validation of the returned `input` to the CALLER (InsightSession in T6 will Codable-decode `[String: Any]` → `InsightSkeleton`). T1's job is only to deliver the dict; T6's job is to validate and fall back to "single prose section" InsightSkeleton on validation failure (per Acceptance Criterion in tech-spec line 568-569).
- Sanitize at the THROW site, never at the catch site. Every `throw AIProviderError.xxx(...)` involving a string must already have run that string through `sanitize(_:)`.
- The fixture file is for human reading + reviewer hand-trace, not for runtime use. Keep it small (< 4 KB) but realistic.
- Keep the new method body under ~60 lines — request build, fire, parse, return — no helpers needed beyond what already exists.

**Security invariants (security-auditor will verify):**

- API key never appears in any error message, log, or returned value
- No `print(...)` or `NSLog(...)` of the request body or response body without sanitization
- `tool_choice` is set so the model can't emit untrusted free-form text in place of structured output
- No new dependency / no new framework import beyond `Foundation`
