# Проектные процессы разработки MarkU

## Question

Я хочу исследовать такой вопрос, как мне имплементировать software development flow для каждого проекта отдельно. Что я имею ввиду? Иногда, например, нужно pull-requests делать, иногда может быть flow прямой, прямо в main, иногда важно как релизы делать, иногда важно то, иногда все. И, понимаешь, в каждом проекте оно несколько по отдельности. И вот я бы хотел, чтобы у меня был некий конструктор, который, ну, во-первых, там были дефолтные комбинации всегда, а был бы некий такой, так сказать, конструктор, который мог бы мне для проекта соорудить, когда, например, фичи или баги становятся в implementing, когда они переходят из одного в другое, какие условия. И MarkU должен их соблюдать, если мы выделили этот определенный flow. И я хочу понять, какие flow могут быть, как это имплементнуть, как это все совместить со статусом фичи, багов, интеграции с GitHub, в дальнейшем, если это интегрировано. Как AI понимает, когда переводить один статус в другой статус. То есть у нас у MarkU должны быть всякие защиты при переводе из одного статуса в другой. Все эти защиты и правила делаются на каждый проект отдельно.

### Разные статусы feature и bug {#n7}

- tags: статусы

Feature проходит через `idea`, `exploring`, `ready`, `implementing`, `implemented`, `verified` и другие состояния; у bug отдельный набор `open`, `fixing`, `fixed`, `closed`. Конструктор должен настраивать оба жизненных цикла, сохраняя их различия.

#### Evidence

- [Project fact] Оба словаря статусов заданы в коде отдельными массивами. — `MarkView/Models/FeatureVocabulary.swift:5`
- [AI inference] Графы переходов features и bugs стоит конфигурировать отдельно при общей модели правил.

### Сервис переходов уже существует {#n8}

- tags: lifecycle

Есть центральный сервис переходов, журнал, проверка устаревшего состояния и обнаружение внешних изменений Markdown. Его разумно расширять проектной политикой, а не начинать систему с нуля.

#### Evidence

- [Project fact] FeatureStore+Lifecycle связывает IssueTransitionService, журнал переходов и Markdown-статусы; запрос проверяет наблюдавшийся статус. — `MarkView/Models/FeatureStore+Lifecycle.swift:3`
- [Project fact] Внешнее изменение статуса сохраняется как неподтверждённое до подтверждения или разрешения человеком. — `docs/features/issue-lifecycle-management/decisions/DEC-015.md`

### Проектный Definition of Done {#n9}

- tags: настройки, AI

В проекте уже есть настраиваемый чек-лист с режимами `require`, `ask`, `skip`, который передаётся агенту. Его следует связать с проверяемой политикой, поскольку текст цели сам по себе не обеспечивает соблюдение условий.

#### Evidence

- [Project fact] DefinitionOfDone хранит проектный чек-лист и формирует текст цели для ассистента. — `MarkView/Models/DefinitionOfDone.swift:3`
- [AI inference] Инструкция в промпте не является самостоятельным механизмом принудительной проверки перехода.

### Проверка доставки и GitHub {#n10}

- tags: доказательства

Сборщик уже ищет доказательства в Git и GitHub, учитывает неоднозначные связи и недоступность источников. GitHub Sync имеет отдельную логику подтверждённого завершения и расхождений.

#### Evidence

- [Project fact] IssueEvidenceCollector собирает данные Git и GitHub и не считает недоступный обязательный источник пройденной проверкой. — `MarkView/Models/IssueEvidenceCollector.swift:3`
- [Project fact] IssueGitHubPlanner рассматривает закрытие, повторное открытие и расхождения; GitHub не меняет локальный статус напрямую. — `MarkView/Models/IssueGitHubSync.swift:24`

### Шаблоны и конструктор {#n3}

- tags: настройка

Типовые комбинации ускоряют настройку, а проектные правила позволяют адаптировать её.

- [AI inference] Шаблон может задавать начальную конфигурацию, которую проект затем уточняет.

### Готовые комбинации {#n11}

- tags: шаблоны

Предложить несколько стартовых шаблонов: прямые commits в основную ветку; короткая ветка и PR; PR с review и CI; релизный процесс с обязательной публикацией. Шаблоны задают начальные значения, а не ограничивают дальнейшую настройку.

#### Evidence

- [External fact] GitHub описывает GitHub flow как процесс с веткой, изменениями и pull request. — <https://docs.github.com/en/get-started/using-github/github-flow>
- [AI inference] Прямой commit, PR, review, CI и выпуск можно комбинировать как независимые настройки.

### Из чего собирается flow {#n12}

- tags: конструктор

Разделить настройки по объекту работы, целевой ветке, способу доставки, проверкам, приёмке и выпуску. Для каждого перехода задать разрешённых инициаторов, событие, условия и действие после успеха.

#### Evidence

- [AI inference] Независимые параметры позволяют выразить сочетания правил без отдельного жёстко заданного шаблона для каждого варианта.

### Разные правила внутри проекта {#n13}

- tags: исключения

Предусмотреть общую политику проекта и уточнения для feature, bug и типа изменения. Например, код проходит через PR и выпуск, а документация идёт напрямую в `main`; при неоднозначной классификации требуется решение человека.

#### Evidence

- [Project fact] Для MarkView app-изменения проходят через PR и релиз, а документация коммитится прямо в main. — `CLAUDE.md`
- [AI inference] Для сложных исключений нужен явный порядок приоритетов и объяснение выбранного правила.

### Граница документационного исключения {#n32}

- tags: классификация

Исключение применяется к изменениям, состоящим только из документации. Смешанное изменение требует отдельной классификации всей поставки, а не выбора правила по одному файлу.

#### Evidence

- [Project fact] Для documentation-only изменений предусмотрен прямой коммит в main; для остальных feature и bug fix — отдельная ветка и PR. — `CLAUDE.md:59`
- [AI inference] Для смешанного набора файлов нельзя автоматически применять исключение только потому, что в нём есть документация.

### Состав и неизвестные файлы {#n33}

- tags: пути, неизвестно

Текущая проверка считает документацией `docs/`, `tasks/` и файлы `.md`; пустой или неизвестный список файлов не подтверждает документационное исключение. Правила для других форматов документации следует задать явно.

#### Evidence

- [Project fact] DocumentationPaths распознаёт пути внутри docs/ и tasks/ и файлы с суффиксом .md; WorkUnit требует непустой известный список. — `MarkView/Models/IssueLifecycleEvidence.swift:83`
- [Project fact] Руководство включает в documentation-only изменения presentations, но проверка путей не содержит общего правила для их форматов. — `CLAUDE.md:59`
- [AI inference] Несовпадение областей действия руководства и классификатора требует явного решения о форматах и контексте файлов.

### Тип задачи и тип изменения {#n34}

- tags: feature, bug

Разделить два независимых признака: feature или bug описывает задачу, а состав изменения определяет применимость исключения для документации. Это позволяет документационной работе по bug следовать документационному правилу, если проект явно выбрал такую политику.

#### Evidence

- [Project fact] Модель различает виды задачи feature и bug, а documentation-only определяется отдельно по изменённым путям. — `MarkView/Models/IssueSync.swift:8`
- [Project fact] Классификация documentation-only требует, чтобы каждый изменённый путь был документационным. — `MarkView/Models/IssueLifecycleEvidence.swift:83`
- [Open assumption] В проекте допустимо применять документационное исключение к задаче любого вида; это следует подтвердить в политике.

### Приоритет пересекающихся правил {#n35}

- tags: приоритет, конфликт

Задать явный порядок: общая политика, затем применимое уточнение по виду задачи и составу изменения; конфликт или неполные данные передавать человеку. При нескольких применимых требованиях безопасный выбор до решения проекта — сохранять более строгие условия.

#### Evidence

- [Project fact] ProjectDeliveryPolicy начинает с checklist и распознаёт определённые явные правила руководства как переопределение; обязательный PR имеет приоритет перед распознанным разрешением прямых коммитов. — `MarkView/Models/IssueLifecycleEvidence.swift:98`
- [AI inference] Общий порядок приоритетов и обработка конфликтующих локальных уточнений здесь предложены как дизайн, а не как существующая универсальная реализация.
- [Open assumption] Применение более строгого требования до решения человека соответствует желаемой политике проекта.

### Последствия выбранного типа {#n36}

- tags: версия, выпуск

Классификация должна определять независимые требования: способ доставки, повышение версии, проверки и выпуск. Для build scripts в руководстве есть отдельное правило версионирования, поэтому их нельзя автоматически приравнивать к документации.

#### Evidence

- [Project fact] Изменения docs, tasks или только build scripts не повышают версию; для изменений приложения применяется semantic versioning. — `CLAUDE.md:81`
- [Project fact] Для app-changing feature или bug fix требуются PR и выпуск, а docs-only изменение не требует app build или DMG. — `CLAUDE.md:121`
- [AI inference] Отдельные последствия позволяют описать категорию изменения, для которой часть требований отличается от правил приложения и документации.

### Версионируемая политика проекта {#n14}

- tags: конфигурация

Хранить структурированную политику в проекте: версия схемы, шаблон, статусы, переходы, проверки и параметры интеграций. Конструктор должен показывать итоговые правила, проверять противоречия и давать протестировать сценарий до сохранения.

#### Evidence

- [AI inference] Явная машиночитаемая конфигурация уменьшает зависимость выполнения правил от интерпретации свободного текста агентом.
- [Open assumption] Команда хочет разделять одну и ту же политику между участниками через репозиторий; расположение и способ синхронизации нужно согласовать.

### Единственный источник правил {#n15}

- tags: миграция

Определить приоритеты между новой политикой, `DefinitionOfDone` и инструкциями проекта; при конфликте показывать его человеку. Перенести существующие настройки с сохранением прежнего поведения и фиксировать версию политики в истории переходов.

#### Evidence

- [Project fact] Текущий ProjectDeliveryPolicy выводит требования PR и CI из Definition of Done и распознаёт некоторые явные инструкции в руководстве проекта. — `MarkView/Models/IssueLifecycleEvidence.swift:98`
- [AI inference] Без правил приоритета агент и проверяющий сервис могут получить разные ответы о том, что обязательно.

### Переходы и защиты {#n4}

- tags: состояния

Явные события, условия и подтверждения определяют, когда разрешён переход.

#### Evidence

- [AI inference] Проверка перехода должна быть отдельна от решения AI предложить переход.

### Начало работы {#n16}

- tags: старт

Для типового автоматического перехода в `implementing` или `fixing` использовать успешную передачу задачи агенту либо привязку сессии. Для ручной работы можно добавить отдельное явное событие начала, если это разрешено политикой проекта.

#### Evidence

- [Project fact] Текущие правила требуют startEvidence; оно представлено успешным handoff или привязкой AI-сессии. — `MarkView/Models/IssueLifecycle.swift:39`
- [AI inference] Ручное начало работы потребует определённого проектом подтверждения, если его нужно учитывать без AI-сессии.

### Доставка и приёмка {#n17}

- tags: завершение

Отделить завершение реализации от приёмки: `implemented` или `fixed` — выполнены применимые условия доставки; `verified` или `closed` — выполнена требуемая проверка результата. Проект выбирает, необходимы ли merge, конкретные CI-проверки, релиз и чья приёмка достаточна.

#### Evidence

- [Project fact] В действующем решении завершение реализации и приёмка разделены; решение предусматривает merge, обязательные проверки и необходимый релиз. — `docs/features/issue-lifecycle-management/decisions/DEC-007.md`
- [Project fact] Для AI-приёмки текущая политика требует текст проверки, а для feature — также отмеченные критерии приёмки. — `MarkView/Models/IssueLifecycle.swift:133`

### Важное расхождение реализации {#n18}

- tags: расхождение

Перед расширением нужно разрешить расхождение между принятым решением и кодом: сборщик сейчас отключает требования PR и CI для features и определяет обязательность релиза только для bugs. Нельзя считать release-inclusive правило уже одинаково работающим для обоих типов.

#### Evidence

- [Project fact] Решение DEC-007 описывает завершение после merge, обязательных проверок и необходимого релиза. — `docs/features/issue-lifecycle-management/decisions/DEC-007.md`
- [Project fact] IssueEvidenceCollector вычисляет releaseRequired только для bug, а для feature выключает checksRequired и pullRequestRequired. — `MarkView/Models/IssueEvidenceCollector.swift:40`

### Результат проверки условий {#n19}

- tags: защиты

Каждое условие возвращает выполнено, не выполнено или неизвестно с причиной и источником. При неизвестных или устаревших данных автоматический переход блокируется; пользователь видит, чего не хватает и как это исправить.
