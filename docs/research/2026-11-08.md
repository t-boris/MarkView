# UIStudio для приложений macOS

Я хочу, чтобы ты сделал research, насколько сложно будет сделать UIStudio подключить для маковских приложений, чтобы мы видели маковское приложение в UIStudio. ## Nodes

### UIStudio для приложений macOS {#n1}

- tags: macOS, исследование

Подключить нативное macOS-приложение к UIStudio **возможно**, если запускать его как отдельный процесс и подготовить контролируемые зависимости. Первая версия для одного адаптированного приложения выглядит реализуемой; универсальная поддержка произвольных приложений с полным набором возможностей нынешнего Studio значительно сложнее и не гарантирована.

#### Evidence

- [Project fact] MarkView — нативное приложение macOS на SwiftUI, AppKit и WKWebView. — `CLAUDE.md`
- [AI inference] Запуск отдельного процесса, захват окна и явная подмена зависимостей образуют реалистичный путь интеграции, который ещё необходимо проверить прототипом.

### Текущая архитектура UIStudio {#n2}

Нужно установить существующий механизм запуска, отображения и подмены зависимостей.

### Сегодня Studio ориентирована на Web {#n7}

- tags: граница

Нынешний UI Studio запускает настоящий клиентский веб-интерфейс; SwiftUI указан за пределами исходного объёма. Это расширение потребует отдельного нативного адаптера.

#### Evidence

- [Project fact] В описании функции поддержаны клиентские веб-интерфейсы и браузерный Electron renderer; native SwiftUI execution исключён из Scope. — `docs/features/markview-ui-studio/overview.md`

### Что можно переиспользовать {#n8}

- tags: повторное использование

Сценарии, симулятор, локальный gateway, история и визуальные свидетельства — основа для исследования повторного использования. Их подключение к нативному процессу нужно реализовать отдельно.

#### Evidence

- [Project fact] Симулятор хранит состояние сценария и возвращается к исходным данным при reset; gateway принимает запросы на loopback и передаёт их симулятору. — `MarkView/Models/UIStudioSimulation.swift:157`
- [Project fact] Интерфейс содержит панели истории, сценариев, окружения и свидетельств. — `MarkView/Views/UIStudioView.swift:25`
- [Project fact] Gateway маршрутизирует обращения к имитируемым сервисам в симулятор с локальных портов. — `MarkView/Models/UIStudioGateway.swift:4`

### Что придётся заменить {#n9}

- tags: инспектор

Встраивание WKWebView, DOM-выделение и привязка к исходникам веб-приложения не работают напрямую для SwiftUI или AppKit. Нужны новый просмотрщик, нативный инспектор и стратегия определения исходного кода.

#### Evidence

- [Project fact] Веб-версия описывает DOM selection и инструментирование для связи элементов с исходниками. — `docs/features/markview-ui-studio/overview.md`
- [Project fact] Выбор элемента разрешает позиции JavaScript через source map dev server. — `MarkView/Models/UIStudioSelection.swift:246`
- [AI inference] DOM и source maps JavaScript не предоставляют соответствия между элементами интерфейса другого нативного процесса и строками Swift.

### Способы запуска macOS {#n3}

Варианты интеграции различаются глубиной взаимодействия и системными ограничениями.

### Запуск и изображение окна {#n10}

- tags: рекомендуемый путь

Практический вариант — собрать и запустить отдельный процесс приложения, захватывать его окно и показывать поток в Studio. Это изображение другого окна, поэтому клавиатуру, мышь, масштаб, фокус и несколько окон придётся отдельно согласовать; настоящая интерактивность требует прототипа.

#### Evidence

- [External fact] ScreenCaptureKit поддерживает захват отдельного окна, независимый от дисплея. — <https://developer.apple.com/videos/play/wwdc2022/10156/>
- [AI inference] Поток кадров сам по себе не переносит владение окном и не обеспечивает передачу ввода, корректную геометрию или жизненный цикл приложения.

### Выбор нативных элементов {#n11}

- tags: Accessibility

Accessibility API позволяет исследовать доступные элементы другого процесса и выполнять поддерживаемые действия. Покрытие зависит от accessibility целевого приложения, а привязка к строкам Swift потребует инструментирования или вероятностного поиска с указанием уверенности.

#### Evidence

- [External fact] Apple предоставляет верхнеуровневый accessibility-объект приложения по идентификатору процесса. — <https://developer.apple.com/documentation/applicationservices/1459374-axuielementcreateapplication?language=objc>
- [AI inference] Accessibility-дерево не гарантирует наличие каждого визуального элемента или точного местоположения в исходном коде.

### Разрешения и границы {#n12}

- tags: разрешения

Для захвата и управления могут потребоваться системные разрешения на запись экрана и Accessibility. Поведение при запрете должно быть явным, а поддержка macOS 13 и более новых версий — проверена на практике.

#### Evidence

- [External fact] macOS позволяет пользователю управлять доступом приложений к записи экрана. — <https://support.apple.com/en-euro/guide/mac-help/mchld6aa7d23/27/mac/27>
- [External fact] Доступ стороннего приложения к управлению через accessibility требует специального разрешения пользователя. — <https://support.apple.com/en-ie/guide/mac-help/mh43185/27/mac/27>
- [Project fact] Поддерживаемая нижняя версия MarkView — macOS 13. — `CLAUDE.md`

### Альтернатива: отдельные представления {#n13}

- tags: альтернатива

Для приложений с подготовленными компонентами возможен отдельный host с тестовыми данными; Xcode Preview подтверждает возможность показывать отдельные SwiftUI и AppKit представления. Это подход для адаптированных экранов, а не готовый способ встроить произвольное приложение целиком в Studio.

#### Evidence

- [External fact] Xcode previews отображают SwiftUI и AppKit views, позволяют задавать настройки и пример данных без запуска полного приложения. — <https://developer.apple.com/documentation/xcode/adding-previews-to-your-interface-files>
- [AI inference] Реализация собственного host потребует совместимой точки входа и доступа к зависимостям приложения; документация Xcode не подтверждает общедоступного API для встраивания его canvas в Studio.

### Существующие точки входа Preview {#n29}

- tags: SwiftUI, интеграция

В MarkView уже есть примеры запуска отдельных SwiftUI-представлений: `TOCView` получает `layout` и `WorkspaceManager`, а `FileTreeView` — объект окружения. Это полезные образцы состава host, но не реестр экранов для UI Studio.

#### Evidence

- [Project fact] Preview для TOCView создаёт WorkspaceManager, передаёт его layout и внедряет объект в окружение. — `MarkView/Views/TOCView.swift:215`
- [Project fact] Preview для FileTreeView внедряет WorkspaceManager через environmentObject. — `MarkView/Views/FileTreeView.swift:1016`
- [AI inference] Для собственного host потребуется отдельно определить, какие представления доступны и как их создавать; показанные Preview сами по себе такого реестра не предоставляют.

### Контракт адаптера экрана {#n30}

- tags: host, SwiftUI, AppKit

Host должен получать фабрику выбранного представления и явно собирать его окружение, включая масштаб шрифта и тему. В MarkView уже есть пример встраивания SwiftUI в AppKit через `NSHostingView`; переиспользование кода конкретного приложения зависит от доступа к его типам и настройкам сборки.

#### Evidence

- [Project fact] Окно настроек создаёт NSHostingView с DDESettingsView, workspace, масштабом шрифта и темой. — `MarkView/App/MarkViewApp.swift:539`
- [Project fact] В project.yml объявлен один application target MarkView, включающий исходники MarkView. — `project.yml:23`
- [AI inference] Для подключаемых экранов нужен явный контракт фабрики и способ сборки совместимых типов; текущий application target сам по себе не определяет интерфейс плагина.

### Сборка и ресурсы host {#n31}

- tags: сборка, ресурсы

Адаптер должен поставлять не только код представления, но и необходимые ресурсы целевого приложения. Например, редактор MarkView ищет HTML через `Bundle.main`, поэтому перенос его в другой исполняемый bundle требует решения для путей ресурсов.

#### Evidence

- [Project fact] EditorView ищет index.html в Bundle.main и загружает страницу редактора из bundle приложения. — `MarkView/Views/EditorView.swift:47`
- [Project fact] Сборка MarkView копирует ресурсы Editor в папку ресурсов приложения. — `project.yml:31`
- [AI inference] При отдельном host ресурсам нужен корректный bundle или адаптированный поиск; доступность одного Swift-типа не гарантирует работоспособный экран.

### Жизненный цикл и изоляция {#n32}

- tags: жизненный цикл, изоляция

Создание представления может запустить логику приложения ещё до взаимодействия с ним. Поэтому host следует проектировать с управляемым созданием и завершением объектов, а для безопасности и повторяемости проверить отдельный процесс и очищаемое состояние.

#### Evidence

- [Project fact] Инициализация WorkspaceManager создаёт каталог Application Support, запускает agentActivity и читает UserDefaults и недавние файлы. — `MarkView/Models/WorkspaceManager.swift:633`
- [AI inference] Отдельный процесс может ограничить влияние сбоев и упростить сброс состояния, но сам по себе не запрещает доступ к пользовательским данным или побочные эффекты.

### Границы достоверности экрана {#n33}

- tags: точность, композиция

Изолированное представление нужно проверять в подходящем размере и оконном окружении: иначе его поведение может отличаться от приложения. Составной экран может включать как SwiftUI, так и AppKit или WebKit, поэтому готовность одного компонента не означает готовности всего экрана.

#### Evidence

- [Project fact] Окно настроек задаёт размеры NSWindow и помещает в него NSHostingView с настроенным корневым представлением. — `MarkView/App/MarkViewApp.swift:522`
- [Project fact] DiscussionThreadView представляет WKWebView через NSViewRepresentable и загружает HTML из bundle. — `MarkView/Views/DiscussionThreadView.swift:4`
- [AI inference] Для оценки сходства host с приложением нужны проверки конкретного экрана в обоих окружениях, включая размеры, фокус и взаимодействия.

### Имитация зависимостей {#n4}

Воспроизводимые состояния требуют контроля над данными, процессами и внешними сервисами.

### HTTP и сценарии {#n14}

- tags: HTTP

Если приложение позволяет настроить адреса сервисов, его можно направить на существующий loopback gateway и использовать сценарии Studio. Для URLSession возможен дополнительный адаптер в коде приложения, но это не универсальный перехват любого трафика.

#### Evidence

- [Project fact] Gateway запускает локальный listener для переменных адресов сервисов и передаёт запросы симулятору. — `MarkView/Models/UIStudioGateway.swift:4`
- [External fact] URLSessionConfiguration поддерживает пользовательские URLProtocol для соответствующей сессии; они недоступны для background sessions. — <https://developer.apple.com/documentation/foundation/urlsessionconfiguration/protocolclasses>
- [AI inference] Приложению нужна конфигурация URL, внедрение зависимости или другая явно поддержанная точка подключения; гарантировать охват сторонних SDK и всех сетевых стеков нельзя.

### Локальные данные и побочные эффекты {#n15}

- tags: изоляция, reset

У нативных приложений backend — лишь часть окружения: нужны отдельные тестовые файлы, настройки, база, учётные данные и контролируемый запуск процессов. Reset должен восстанавливать и данные симулятора, и состояние самого приложения; существующий веб-reset этого не обеспечивает автоматически.

#### Evidence

- [Project fact] WorkspaceManager использует UserDefaults, Application Support и базу рабочего пространства. — `MarkView/Models/WorkspaceManager.swift:635`
- [Project fact] Существующее восстановление содержит специальные механизмы для cookies и localStorage браузера. — `MarkView/Models/UIStudioSession.swift:1943`
- [AI inference] Для воспроизводимости нативной сессии потребуется отдельный тестовый профиль и управляемые адаптеры локального состояния; приложение может иметь и неподменяемые системные интеграции.

### Проверка тем MarkView {#n16}

- tags: целевой документ, темы

Для выбранной задачи важен сценарий с несколькими окнами, независимыми темами и акцентами, восстановлением после перезапуска и сохранением несохранённых правок. Проверять надо и нативные поверхности, и встроенные WKWebView, поскольку захват окна показывает результат всей композиции.

#### Evidence

- [Project fact] Критерии требуют независимые настройки окон, восстановление темы и акцента, согласованное оформление редактора, Markdown, discussion и terminal и сохранение состояния документов. — `docs/features/per-window-themes/overview.md`
- [Project fact] Редактор создаёт WKWebView внутри нативного приложения. — `MarkView/Views/EditorView.swift:5`
- [AI inference] Нужно проверить оба окна и обе их темы в одном сценарии: снимок единственного окна не доказывает независимость.

### Неизвестные интеграции {#n17}

- tags: покрытие

Автоматическое обнаружение контрактов Swift, сериализации, сервисных адресов и начального состояния — отдельная сложная задача. Для первой версии разумно требовать явную конфигурацию и показывать список неподдержанных реальных соединений.

#### Evidence

- [Project fact] Исходный Scope UI Studio исключает универсальную симуляцию приложений и требует раскрывать ограничения неподдерживаемых зависимостей. — `docs/features/markview-ui-studio/overview.md`
- [AI inference] Статический анализ и AI могут предложить конфигурацию, но не доказывают полноту перехвата и корректность имитации.

### Сложность и план проверки {#n5}

Оценка зависит от выбранного уровня интеграции и результатов прототипа.

### Предварительная оценка {#n18}

- tags: оценка

Для одного подготовленного SwiftUI/AppKit приложения: прототип запуска, окна и одного mock API — примерно 1–3 инженерные недели; пригодная первая версия с изоляцией, сценариями и базовым инспектором — 6–12 недель. Универсальная поддержка произвольных приложений с качеством нынешнего Web Studio — несколько месяцев и выше, без гарантии полной совместимости.

#### Evidence

- [AI inference] Диапазоны – грубая оценка для одного опытного инженера при доступном исходном коде и собираемом проекте; они не основаны на измеренном прототипе и не включают неизвестные организационные задержки.
- [Open assumption] Для первой версии приложение допускает test-mode и явную настройку mock endpoints; не требуется полная поддержка произвольных закрытых бинарников.

### Первый проверочный прототип {#n19}

- tags: план

1. Собрать и запустить изолированную копию MarkView с тестовым workspace. 2. Показать её окно внутри Studio и проверить ввод, фокус, resize и две macOS версии. 3. Подключить один mock endpoint и reset, затем воспроизвести переключение тем в двух окнах. 4. Выбрать элемент через Accessibility и оценить привязку к исходнику.

#### Evidence

- [AI inference] Такой прототип одновременно проверит самые рискованные технические допущения: интерактивность трансляции, изоляцию, управление состоянием и доступность элементов.
- [Project fact] Целевой документ требует независимости окон и сохранения документа и состояния панелей при изменениях темы. — `docs/features/per-window-themes/overview.md`

### Критерии решения {#n20}

- tags: go/no-go

Продолжать к MVP, если трансляция остаётся интерактивной, целевой сценарий воспроизводится после reset, реальная сеть не используется без явного разрешения, а найденные элементы можно надёжно соотнести с кодом хотя бы в ограниченном наборе экранов. Иначе начать с отдельного окна приложения и скриншотов, а ограничения озвучить пользователю.

#### Evidence

- [AI inference] Ограниченный сценарий с измеряемыми результатами позволяет отделить техническую возможность демонстрации от полноценной поддержки рабочего процесса Studio.

### Что сильнее всего влияет {#n21}

- tags: неопределённость

Оценку меняют необходимость запуска без изменений целевого кода, требование настоящего встроенного окна, точность перехода от элемента к исходнику, поддержка сторонних SDK и системных диалогов, а также число одновременно работающих окон.

#### Evidence

### Запуск и изображение окна {#n23}

### Выбор нативных элементов {#n24}

- tags: Accessibility

Accessibility API позволяет исследовать доступные элементы другого процесса и выполнять поддерживаемые действия. Покрытие зависит от accessibility целевого приложения, а привязка к строкам Swift потребует инструментирования или вероятностного поиска с указанием уверенности.

#### Evidence

- [External fact] Apple предоставляет верхнеуровневый accessibility-объект приложения по идентификатору процесса. — <https://developer.apple.com/documentation/applicationservices/1459374-axuielementcreateapplication?language=objc>
- [AI inference] Accessibility-дерево не гарантирует наличие каждого визуального элемента или точного местоположения в исходном коде.
