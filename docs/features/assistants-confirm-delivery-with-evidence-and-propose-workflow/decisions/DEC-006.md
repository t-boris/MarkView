## Context

Boris wants a workflow in which taking an item into development or finishing an investigation moves it to review by itself. Today a rule says only who may make a step with what evidence, and MarkView moves an item by itself only on delivery evidence, on a regression report and in the AI flows of the app.

## Alternatives

1. A separate list of automations next to the rules (a second place that must stay consistent with the transition table)
2. Events as conditions of a rule (a condition says what must be true before a step, not what makes it happen)
3. Any event, including file or time based ones (needs detection that the app does not have)

## Decision

A transition rule gets one optional field naming the event after which MarkView makes the step. The first set is the events the app already sees: work-started, investigation-finished and pull-request-merged. MarkView acts as the system actor under the rule's system conditions, once per item and event, and only for items that were in the from-statuses when the event happened. Further events are added the same way later.

Change during implementation (2026-11-09): the accepted list also named pull-request-opened. Reading the code showed that the app observes only merged pull requests, not open ones, so that event was left out instead of being promised and never firing. work-started means any start step of the item (hand-off, attached session, or a person starting it).

## Reason

The rule already says from, to and what MarkView (system) needs; the event completes it in the same place, the editor, the diagram and the validation that exist keep working, and the first events need no new detection.

## Consequences

The format gains one optional field per rule; the history gains the event on a record. Each event has one hook where the app already knows the fact (the start step, the end of the bug investigation, the GitHub sync of merged pull requests). pull-request-opened needs new detection and can be added later in the same way.
