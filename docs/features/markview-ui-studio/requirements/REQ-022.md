## Statement

The system shall answer an application's generated requests in the response envelope its transport expects, shall let a request that answers or dismisses something change what another request lists, and shall prepare the rule for a request a scenario names instead of refusing the scenario.

## Acceptance Criteria

- [x] A rule-less generated list, detail, create, update, delete and empty answer are wrapped by the environment's envelope for the rule's service (origin or path prefix); fixed answers and overrides are sent as they are; a list already under the result key is not wrapped twice; a failed answer uses the envelope's failure shape.
- [x] A get, update or delete rule with `idParam` finds the record's id in the JSON body (then the query) when its path has no id parameter.
- [x] The assistant is told what `envelope` means, where the transport's wrapper goes (`envelopes`), how arguments in the body are named (`idParam`) and that a request that changes what another lists is modelled on one entity with a channel link; the validator refuses a template in `envelope`.
- [x] An environment without `envelopes` is reviewed once after the map (when automatic repair is on): the envelope is saved (an empty list means none), template `envelope` strings are cleaned, fixed list/action groups are re-modelled, and the page loads again; a reviewed environment, or one with automatic repair off, is never asked again.
- [x] A context change naming a request no rule serves has the rule prepared once and then succeeds; when it cannot be prepared it is refused as before.
- [x] A screen request asks for the screen without a blocking dialog in front of it, and the assistant is told to take such a cover away in the scenario unless the screen is that dialog.
- [x] On a copy of product-promotion-desk with the real assistant, the Products page lists its products and pressing "I'm done" in the pending-question dialog removes that question (1 of 6 becomes 1 of 5).
