## Context

REQ-017 (2026-11-04) offered Fix data only on a click: "Nothing happens without the click". On 2026-11-14 Boris reported that UI Studio very often shows an error at open (a sign-in is needed, or the simulated data is wrong), that he cannot find where Fix is, and asked that Studio repair such errors itself. Real session logs (vivaa-platform, product-promotion-desk) show the same causes: a redirect to a sign-in page, requests without a rule after a 90 s preparation timeout, a blocked third-party script, a data error. Fix data was offered only for errors of the current page generation, so every scenario switch removed it, and the other problem rows had no action at all.</context>
<parameter name="alternatives">["Keep the click, make the button more visible (an offered but weaker answer)", "Automatic only for sign-in and requests without a rule; data errors stay on the button", "Fully automatic with no limit (rejected: loops and cost, an error data cannot fix would be retried forever)"]

## Decision

UI Studio repairs the problems it can repair by itself, after the page has settled at open and after later page errors: a data error goes through the existing Fix data contract (records only), a request without a rule gets one more preparation and the page reloads, a redirect to a sign-in page is answered by the assistant-made signed-in scenario (the REQ-010 path), saved so the next open replays it. Code errors and blocked third-party scripts are only reported. Each problem in the Log has its own action and the Log has a Fix problems button; the actions act on the error, not on the page generation. Repair is bounded (a ledger per scenario and error, no repeat of an error judged not data or refused, 2 attempts per error, 3 automatic repairs per open), visible (a Log notice with the reason and a banner) and undoable for the running session. A project switch turns it off. Stale-generation rejections are answered silently and are not problems. This replaces REQ-017 criterion 5.

## Reason

Boris asked for it (2026-11-14), and the logs show that the failures are repeated and mechanical. The risks that made the click necessary (a model changing data without being asked) are answered by validation on a copy before anything is saved, by the limits, by the visible notice and by Undo, not by a click. The classification of problems is by deterministic rules, never by the model, so the repair does not depend on the model's judgement of what to repair.</reason>
<parameter name="consequences">An assistant call may start without a click, up to 10 minutes and 2 calls per error in the worst case. Tests must prove that nothing loops and that nothing runs while the session is busy, mapping, preparing or trying a scenario. REQ-017 criterion 5 is superseded. The click stays available (Fix problems, a row action). Undo is kept for the running session only.</consequences>
