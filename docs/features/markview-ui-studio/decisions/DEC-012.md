## Context

The application connection policy (REQ-006) blocks every script of another origin that the person did not allow. A page of vivaa that loads Stripe.js (`https://js.stripe.com/v3`) therefore failed in UI Studio: `@stripe/stripe-js` rejected with "Failed to load Stripe.js", nothing caught the rejection, the page showed the framework's error overlay or stayed empty, and Fix data correctly answered that no record caused it (BUG-103). The simulation covers fetch, XHR, sockets and external navigation, but nothing answers a script. Boris asked for UI Studio to continue with a simulation or a graceful fallback when an external service is not available, and chose (2026-11-07) Stripe, reCAPTCHA, Google Maps and analytics in one change, with a placeholder payment form whose outcome follows the scenario.

## Alternatives

1. Allow the SDK's address in Environment settings: the real script loads, but its frames and api.stripe.com stay blocked, so Elements do not work, and every project has to do it by hand; it also lets requests leave the Mac.
2. Keep blocking and only explain it better (Fix data, the log): the page stays broken.
3. Replace the script at the network level with a local proxy or scheme handler: https cannot be intercepted by WebKit without a proxy and a certificate, which is new infrastructure and a larger trust boundary.
4. Stand-ins inside the page runtime for a registered list of SDK addresses (chosen).

## Decision

The page runtime keeps a registry of SDK script addresses. When the policy blocks a script of a registered address, the runtime defines that SDK's global as a local stand-in before the next script runs, swallows the script's error event, calls the callback the address names (`callback=`, `onload=`) and gives the element its `load` event. Registered: Stripe.js, reCAPTCHA, Google Maps, Google Analytics and Tag Manager, Segment, Mixpanel, PostHog, Plausible. The connection policy itself does not change: no request is sent, no frame is opened. What an SDK would draw is a placeholder labelled as simulated ("Simulated payment — no card is charged"), the session lists it as a simulated dependency, and a payment succeeds, or is declined with `card_declined` when the scenario is an error scenario. An address the person allowed is never replaced; an SDK that is not registered stays blocked and is reported as before.

## Reason

It keeps REQ-006 intact (nothing new leaves the Mac), needs no configuration, works for every project that loads these SDKs, and makes a payment page usable in a mock-up (DEC-007) while it stays visibly different from a real integration. A registry makes the next SDK a small addition.

## Consequences

A stand-in is not the SDK: it accepts the calls pages make and answers plausible results, no real card, map tile, geocoding result or analytics event exists. A method a stand-in does not simulate answers an error that names it (Stripe) or does nothing (Maps, analytics) and is reported once. Only registered addresses are covered; any other blocked SDK still breaks the page it is needed by, and the person must allow its address or add an entry. Stand-ins are maintained code: a vendor's API change needs a change here.
