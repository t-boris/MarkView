## Context



## Alternatives

1. Wrap every answer including fixed ones (double-wraps the existing fixed answers)
2. An `envelope` template string per rule (what the assistant wrote when nothing explained the field; fragile, validated nowhere)
3. Detect the transport in the simulator from the page's requests (needs a page that works, which is the failure)

## Decision

The environment records how an application's transport wraps what it reads (`envelopes`: prefix, resultKey, successFields, failure). The simulator wraps only what it generates from state (list, get, create, update, delete, session, document); fixed `respond` answers and scenario overrides are sent verbatim, and a list already under the result key is not wrapped twice. A rule's `idParam` also resolves the record id from the JSON body, then the query. A rule's `envelope` stays the plain name of the key a list is wrapped in. An environment prepared before this existed is reviewed once by the assistant (envelopes plus fixed list/action groups re-modelled as one entity with a channel link that pushes the change event); an empty `envelopes` list means "looked at, none" and the review is never repeated. A scenario naming a request no rule serves gets that rule prepared instead of being refused.

## Reason

A page of product-promotion-desk crashed with `undefined is not an object (evaluating 'envelope.error.code')` because its transport needs `{ok:true,result}` and the simulator could only produce `{result:[...]}`; its pending-question dialog could never be dismissed because both the list and the answer were fixed bodies without state or change event; and a screen request was refused for naming a request no rule served. Wrapping per rule would double-wrap the 23 fixed answers the project already holds in the application's shape.

## Consequences

New optional field `envelopes` in environment.json (old files decode unchanged). One assistant call (about $0.1) per project at the first open after the update, once. Modelled state transitions are model-dependent: the deterministic part is the validator and the replay of the write; the live check on the real assistant is reported honestly.
