## Context

The generated Appearance screen of a code-derived prototype is unreliable (strikedesk got a stub), and the screens are written by an assistant that does not read the copied stylesheets. The stylesheets of every theme are already in the prototype, and most web applications switch themes with an attribute or class on the root element.

## Alternatives

1. Ask the assistant to build a theme switcher into the generated shell and settings screen.
2. Studio finds the themes in the copied stylesheets and applies the choice to the preview itself (chosen).

## Decision

Studio reads the copied stylesheets for root attribute selectors such as [data-theme="x"], takes the default theme from what the build recorded about the application (or none), shows a theme picker in the Studio toolbar, applies the choice to the preview document and stores it with the prototype. Nothing in the generated files has to know about themes.

## Reason

It works for every code-derived prototype whose stylesheets were copied, needs no assistant run and cannot be broken by a stub or a blank generated screen. The cost is that the picker lives in Studio, not inside the prototype page.

## Consequences

The manifest gains a small theme record (attribute, ids, default, chosen). Only attribute-based themes are found in the first version; class-based and media-query themes are a later extension. A prototype without copied stylesheets has no picker.
