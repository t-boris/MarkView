## Finding

The isolated persistent remote fixture failed after 30 seconds: both home endpoints reported waiting, both work endpoints remained connecting, no fixture process had started and no output was received. This scenario passed locally and in earlier separate hosted runs. The failure does not establish whether the relay, workspace setup or runner scheduling caused the delay. Evidence: `/tmp/markview-ci-qa-arm-failure.log` and [CI run 44317758173](https://github.com/t-boris/MarkView/actions/runs/44317758173).

## Resolution

The isolated relay fixture now records only method, sanitized route and response status; headers, tokens, queries and bodies are excluded. The wrapper prints the last events only on failure and removes the temporary fixture afterward. A local probe confirmed that path, query, header and body secrets are not logged. The real persistent-remote test passed locally against the prebuilt ARM host both on its own in 14.5 seconds (`/tmp/markview-persistent-prebuilt.log`) and in the complete split general QA run in 14.7 seconds (`/tmp/markview-prebuilt-qa-general.log`), including both terminal streams. The [next CI](https://github.com/t-boris/MarkView/actions/runs/44325112808) reproduced the failure: both work sessions and both home session lookups returned HTTP 200, but no mailbox POST was recorded before the deadline (`/tmp/markview-ci-isolated-final.log`). Its preceding independent workspace test took 37 seconds; a delay in workspace description is a hypothesis, not yet established. The cause remains open and the 30-second requirement is unchanged.

For the next CI run, the isolated fixture wrapper samples only the exact test-host executable under its own DerivedData path, and prints selected stack frames only if the fixture fails. It never targets the installed MarkView application. This is diagnostic evidence collection, not a resolution.

The [sampled ARM CI run](https://github.com/t-boris/MarkView/actions/runs/44329444032) reproduced the failure and located both work endpoints inside Foundation's `ProcessInfo.hostName` getter, called by `RemoteWorkspace.describe()`, waiting on a system semaphore (`/tmp/markview-ci-sampled-failure.log`). The workspace now obtains the kernel hostname directly with `gethostname`, avoiding name-resolution waits, and the hosted workspace test verifies the returned hostname. The app version was bumped to 7.0.12. The full local hosted lane passed, including the workspace assertion and both persistent terminal sessions in 14.6 seconds (`/tmp/markview-lane3-hostname.log`); GitHub verification remains open. The 30-second requirement remains unchanged.
