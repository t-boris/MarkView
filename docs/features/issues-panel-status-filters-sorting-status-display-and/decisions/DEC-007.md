## Context

REQ-002/DEC-003 require sorting by priority on one common scale, but no value sets or mapping are defined (F-003). Project facts: the code reads bug `severity` with values like critical/high and treats blocker/high as severe for findings. No feature `priority` field is read today (Q-002).

## Alternatives

1. A: 4-level scale critical > high > medium > low; bug severity maps directly (blocker → critical); optional feature `priority` accepts the same words or P0–P3 (P0 → critical … P3 → low); missing or unknown values count as empty and go last
2. B: Numeric priority 1–5 for both types; severity words converted to numbers
3. C: Sort bugs by severity only and features by date, with no cross-type scale

## Decision

Option A. Scale ranks: critical=4, high=3, medium=2, low=1. Bug `severity`: blocker|critical → critical, high → high, medium|normal → medium, low|minor|trivial → low. Feature optional `priority`: critical|P0 → critical, high|P1 → high, medium|P2 → medium, low|P3 → low. Matching is case-insensitive and trims whitespace. Absent or unrecognized values are treated as empty and placed last in both directions (DEC-003). Ties keep date-descending order, then the key.

## Reason

It reuses the words the codebase and bug files already use. It accepts the common P0–P3 notation without changing file formats. It also makes REQ-002 testable with a fixed table.

## Consequences

REQ-002 acceptance criteria should reference this table. Features without `priority` will all sort last until someone adds the field, which is expected. Adding new values later means updating the mapping table. The vocabulary could be centralized in FeatureVocabulary.
