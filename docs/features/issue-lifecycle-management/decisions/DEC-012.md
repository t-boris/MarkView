## Context

DEC-007 completes implementation after merge, required checks and any release the project requires; plan I-4 asks to associate work with issues and keep ambiguous, stale or incomplete evidence from completing anything. The records do not define "associated", "merged" or "required release".

## Alternatives

1. Treat every commit that names the feature as implementation work.
2. Take the release requirement from a new setting.

## Decision

A work unit is a pull request or a commit on the default branch that changes at least one non-documentation path (documentation: docs/, tasks/, *.md). It is associated with a feature when it names docs/features/<slug>, carries a line `Feature: <slug>` (the hand-off asks the agent to write it), or names a GitHub issue linked to the feature (a pull request also when it closes such an issue), and with a bug when it names the bug id or its linked issue. A unit is merged when it is reachable from the default branch; direct commits to main count (Boris's workflow). Its checks pass when every workflow run of its head commit completed successfully; no run, a pending run, or an unavailable source is not a pass. A release is required for a unit when the project's definition of done (.dde/definition-of-done.json) requires the deploy item and the unit changes a non-documentation path; it is delivered when a published, non-draft GitHub release was made from a commit that contains the unit. Completion needs at least one merged unit, every associated unit merged, checks passed and, when required, the release delivered. Only units made since the issue was last started or reopened count (earlier rounds of work do not), and documentation-only commits are dropped before anything is counted. A reference that cannot be resolved to one issue, a source that could not be read, evidence older than the unit's current head, a history that does not reach back to the start of the work, or more than 30 commits naming the item is unknown and never completes anything.

## Reason

Follows the existing capture code (pull requests by closing references, direct commits by folder and issue mentions) and the project's own definition of done, so no new setting is needed.

## Consequences

Spec-only features never complete on their own; a person marks them. Without the GitHub integration only the local git part (merge) is available, so checks stay unknown and a person overrides.
