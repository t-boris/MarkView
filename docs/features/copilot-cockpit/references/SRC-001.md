## Summary

The original request describes the intended user experience and architectural division for a project-scoped Copilot Cockpit. It is primary stakeholder input for the feature; its statements are candidates for specification, while implementation details and unresolved operational boundaries still need clarification.

## Content

На основе этого и  испрользую знания о проекте 

Да, **такой Copilot Cockpit мне кажется более удачным интерфейсом для MarkView.** Пользователь начинает с цели, получает предлагаемый план и наблюдает за его исполнением. Граф помогает понять и скорректировать работу, а готовые возможности MarkView выполняют её.

Я бы разделил этот cockpit на три части.

**1. Цель и доступные действия**

Вверху — поле с задачей:

> Проверить создание и редактирование стратегий в Strike Desk, исправить найденные проблемы и получить рабочую сборку.

Рядом — настройки того, что Copilot может делать в рамках этого запуска:

| Возможность | Пример настройки |
|---|---|
| E2E-сценарии | Использовать существующие / создавать дополнительные |
| Проверки | E2E, unit-тесты, анализ логов |
| Баги | Регистрировать / исправлять |
| Сборка | Собирать и запускать приложение |
| Деплой | Выключен / тестовое окружение / выбранное окружение |
| Ограничения | Время, бюджет, число циклов исправления |

Эти переключатели должны реально ограничивать доступные операции. Если исправление выключено, процесс заканчивается отчётом о найденных проблемах. Если выключена сборка, Copilot заранее показывает, какие проверки новой версии станут недоступны.

**2. Предлагаемый flow**

Copilot изучает цель, проект и доступные возможности MCP, затем предлагает конкретный план: какие сценарии использовать, что создать, какие этапы выполнить и при каких условиях закончить.

Пользователь может сказать:

> Деплой убери, проверяй только Paper Account, исправления делай максимум в три прохода.

План и граф обновляются вместе. Редактирование кубиков можно добавить, но текстовые уточнения я бы сделал полноценным способом управления с самого начала.

**До запуска должны быть понятны критерии успеха.** Например: «Все выбранные сценарии прошли на итоговой сборке; оставшиеся блокировки перечислены отдельно». Формулировка «сделать приложение рабочим» слишком неопределённая для автономного цикла.

**3. Выполнение и наблюдение**

После старта граф становится живым: текущий этап подсвечивается, завершённые показывают результаты, ожидающие — причину ожидания.

Рядом я бы показывал:

- **Сейчас:** «Перепроверяет редактирование стратегии».
- **Результаты:** 12 из 18 сценариев проверены; найдено 4 бага; 2 исправления подтверждены.
- **Последнее изменение:** «Новая сборка установлена, началась повторная проверка».
- **Препятствия:** «Два сценария ожидают доступности внешнего API».
- **Управление:** пауза, остановка, изменение цели или ограничений.

Каждый результат кликабелен: сценарий открывается в E2E tab, баг — в разделе багов, сборка — в её логах. Так cockpit связывает уже существующие части MarkView.

Я бы избегал общего «готово на 73%»: при обнаружении новых ошибок объём работы меняется. Полезнее показывать **номер прохода, покрытие сценариев и подтверждённые исправления**.

Архитектурно здесь получается ясное разделение: **Copilot предлагает план; сохранённое определение процесса задаёт этапы и ограничения; Temporal исполняет; MCP MarkView предоставляет действия.** Следующий этап выбирается по результатам и условиям процесса. Внутри конкретного задания агент сохраняет свободу разобраться в проблеме.

Если пользователь меняет цель во время работы, Copilot должен показать, как изменится оставшийся план, и применить обновление на безопасной границе этапа. Уже полученные результаты сохраняются с привязкой к прежнему плану и сборке.

**Для первой версии я бы сделал именно этот cockpit с одним шаблоном «проверить → исправить → перепроверить».** Генерация плана, переключатели возможностей, живой граф и результаты уже дадут цельный пользовательский опыт. А универсальный редактор процессов можно развивать по мере появления других реальных задач.
