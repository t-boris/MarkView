## Context

Boris asked on 2026-11-14 for the run screen to look like a cockpit: instruments (altitude, turns, wind, distance to destination), levers to switch things on and off, and a way to send messages to the supervisor that watches the whole run. Today any change of the controls during a run is a full plan revision: the plan gets a new fingerprint, the person approves it again, and applying it marks the earlier steps skipped and restarts from the chosen step. The gate policy is built once per step, and the supervisor only answers questions the step agent asks; the person has no channel to it.

## Alternatives

1. Every lever flip goes through a new approved plan (safe, but restarts steps and is too heavy for a lever)
2. Levers that can also switch things on during a run (would let the run exceed what the person approved)
3. Levers as indicators only
4. Instruments that simulate flight with invented numbers (misleading on a screen watched for days)
5. Paste the person's message straight into the running agent's terminal (interrupts the agent; the terminal handle is private to the step attempt)

## Decision

The run screen gets an instrument panel whose dials show real values of the run: altitude is the share of steps passed or skipped, distance to destination is the steps left with an estimate of the time left from the steps already passed, fuel is agent time used against the time limit, turns are fix cycles used against their limit, wind is the resistance met (gate refusals, failed or interrupted steps, unanswered supervisor questions, silence), and the pulse is the time since the agent's last sign of life. Levers on the screen can only switch OFF what the approved plan allows (filing bugs, fixing bugs, deployment, the supervisor): the person's cuts are stored with the run, apply at the agent's next call, even during a step, and can be put back up to the approved level, never beyond it. Switching something on that the plan has off, changing a limit, or changing create scenarios, build or checks still goes through a plan revision. The person can send the supervisor notes: a note is stored with the run, the supervisor takes it into account in every later answer, and it is added to the briefing of the next step. A note never interrupts the running agent and cannot widen the controls.

## Reason

A lever the person can flip while the run is going must not need a new approval, and it can skip one only if it cannot give the agents more authority than the person already approved; a type that holds only cuts guarantees that. Real values keep the screen honest for a run that lasts days. A note is the one way to reach the supervisor that needs no new runtime and does not break the step the agent is working on.

## Consequences

The gate evaluates the plan's policy narrowed by the person's cuts on every call, and the supervisor checks its cut before answering. Run records gain optional fields (cuts, notes) and two timeline event kinds, so earlier runs still load. A note reaches an agent only when it next asks the supervisor or when the next step starts. Not delivered by this decision: a graceful hold after the current step and a Resume (the runtime accepts only pause, stop and retry), live changes of limits, and live changes of create scenarios, build and checks. The estimate of time left and the wind score are derived conventions and are labelled so; tokens, cost and context use are still not measured.
