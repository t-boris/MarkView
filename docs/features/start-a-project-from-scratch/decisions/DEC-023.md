## Context

DEC-012 (project-level files under `docs/project/`) and DEC-014 (existing feature layout plus a root `README.md`) are both accepted and contradict each other (plan I-1). MarkView discovers, edits and continues specifications only under `docs/features/<slug>/` (Issues list, Feature tab, guided discovery, Review, Implement with AI); `docs/project/` would need a second discovery and editing model.

## Alternatives

1. `docs/project/` with project-level objects (DEC-012).
2. The existing feature layout plus a root `README.md` (DEC-014).

## Decision

Use DEC-014. The confirmed project is written as `docs/features/<project-slug>/`: `overview.md` holds the brief, `decisions/`, `requirements/` and `questions/` hold what clarification produced, `references/SRC-001.md` holds the original idea and `discussion.md` the answered questions. A root `README.md` restates the brief and points to that folder. Questions that did not block the foundation stay open there and are answered later with the same guided discovery. DEC-012 is superseded.

## Reason

The created project opens as a working specification at once, with no new specification model, and later work (more discovery, Review, features next to it) uses the tools that already exist.

## Consequences

REQ-004 references DEC-023 instead of DEC-012. The project's first specification appears in the Issues list like a feature; its title and README make clear that it describes the whole project. The generated `.gitignore` excludes MarkView's local `.dde/` metadata.
