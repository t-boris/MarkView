## Statement

The system shall compute, for every feature and bug, its stays in the statuses of the project's own workflow from the transition journal, and from them the lead time (created to first completed), cycle time (first active to first completed of the current round), waiting time (created to first active), time in each status, rework count and acceptance lag, using only the roles of the statuses so that the standard, Kanban and custom flows are all measured.

## Acceptance Criteria

- [x] A feature and a bug that moved backlog > in-progress > in-review > done in a Kanban workflow show waiting, cycle time, time in in-progress and in in-review, and lead time
- [x] The same engine measures the standard workflow (idea ... implementing, implemented, verified) without any status name written in the code
- [x] Records with phase baseline or a replace command are not events: an item whose status was rewritten by a flow change has no completion time from that rewrite
- [x] External (unverified) records count but carry a data-quality mark
- [x] An item that was reopened gets a new round; the step durations use the current round and the rework count is 1
- [x] Acceptance lag appears only when the flow has a step from one completed status to another
- [x] Durations use calendar time and the format 2d 3h 15m
