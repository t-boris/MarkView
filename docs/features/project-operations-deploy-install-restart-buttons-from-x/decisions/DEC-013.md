## Context

An operation's command is a free-text string. docs/architecture/security.md:57 requires subprocess arguments as arrays and forbids shell-interpolating user or repo strings. Real deploy commands use shell syntax (&&, pipes, variables). Project fact: the embedded terminal already starts the user's shell with `-l` on a PTY (TerminalSession.swift:238-260), falling back to /bin/zsh. AI inference: a macOS GUI application does not inherit the login shell's PATH, so tools such as kubectl or nvm-managed binaries would not be found without a login shell.

## Alternatives

1. A: Run through the user's login shell: `$SHELL -l -c <command>`, with a documented exception to the security rule
2. B: Split the string into an argument array and exec directly; no shell syntax
3. C: Store the command as an explicit argument array in the operations file; shell features only when the user writes `sh -c` themselves

## Decision

Option A. The process is started as argv [`$SHELL`, `-l`, `-c`, <command>] on a pseudo-terminal, with the operation's working directory as the current directory; `$SHELL` falls back to `/bin/zsh` when unset or empty. The command string is passed as one argv element, byte-for-byte as stored in the operations file and as shown in the confirmation; MarkView performs no substitution, templating, concatenation or escaping on it. The process environment is the application's environment plus whatever the login shell's profile files set; MarkView adds no secrets and no variables other than terminal-related ones (TERM, window size). docs/architecture/security.md records an exception: a project operation is a user-confirmed shell command by design, the rule 'never shell-interpolate' continues to apply to every string MarkView itself composes. REQ-001 is amended with these points.

## Reason

Operations exist to replace what the user types in a terminal, so they must behave the same as in the terminal: shell syntax and the user's PATH. Options B and C break common commands or force users to write argument arrays by hand, which contradicts the hand-editable file of DEC-005. Reusing the same launch convention as the embedded terminal gives predictable behaviour. The injection risk the security rule guards against is addressed by never composing the string and by the native confirmation of the exact string (F-003).

## Consequences

A documented exception to the security rule must be added to security.md. Login-shell start-up adds a small delay and any output printed by profile files appears in the panel. Aliases and functions defined only for interactive shells (e.g. in .zshrc) are not available; this must be stated in the user documentation. 'Executable missing' surfaces as shell exit code 127 rather than a launch error, so the REQ-001 criterion on start failure applies to a missing working directory or shell, and a missing tool is reported as failed with exit code 127. Commands are shell-specific and may behave differently for team members using a different shell.
