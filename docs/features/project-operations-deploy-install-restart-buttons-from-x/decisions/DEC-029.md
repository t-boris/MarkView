## Context

F-018: REQ-013 does not define the click action, the moment of the permission request, or project identification when several projects are open. The 'cancelled' criterion seemed reachable only in a race. DEC-011 requires a notification for every completion, including cancelled. DEC-020 defines cancel as a graceful, escalating termination with a 'cancelling' state, so the process can end noticeably later than the cancel click.

## Alternatives

1. A. Click activates MarkView and opens the operation's output panel; permission requested at first operation start; project name included; cancelled case kept and clarified.
2. B. Click only activates MarkView; permission requested on first app launch.
3. C. Same as A, but the cancelled notification is removed from REQ-013.
4. D. Leave notification details to the implementer.

## Decision

Option A. (1) Clicking the notification activates MarkView, brings the window of the operation's project to the front and opens that operation's output panel. If the project window was closed meanwhile, the click only activates MarkView. (2) macOS notification permission is requested the first time the user starts an operation, after the run confirmation is accepted, and never at app launch. The request does not delay or block the start of the subprocess. (3) The notification contains the project name, the operation label, the environment (if any) and the outcome; for failed, also the exit code. (4) Whether MarkView is frontmost is evaluated at the moment the process ends, not at the moment of the user action. The cancelled notification is posted when the process ends after a cancel while MarkView is not frontmost at that moment. REQ-013 is amended accordingly.

## Reason

A notification that leads directly to the output is the expected behaviour and is most useful for failures. Asking for permission in context gives a higher acceptance rate than asking at first launch, when the user has no reason to agree. The project name is required because several project windows can run operations at once (DEC-008, DEC-027). Evaluating frontmost state at process end makes the cancelled case deterministic and testable, since graceful termination takes time, and keeps REQ-013 consistent with DEC-011.

## Consequences

REQ-013 gets new acceptance criteria for click behaviour, permission timing, project name and the frontmost evaluation moment. The notification must carry the project and operation identifiers so the click can be routed. Output is kept in memory only (DEC-019), so after an app restart a click on an old notification cannot open the output; in that case it only activates MarkView. Open assumption: operations terminated by quit or window close (DEC-021) post no notification, because the user has just confirmed the termination; this should be confirmed by the team.
