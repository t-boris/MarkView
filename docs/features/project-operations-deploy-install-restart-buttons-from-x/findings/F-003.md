## Finding

The same confirmation is shown on every run of every operation, so it does not signal that a command changed since the user last ran or reviewed it (e.g. after `git pull` or a branch switch). DEC-002 itself records the 'risk of habitual confirmation'. The overview criterion 'If the discovered command later changes, confirmation is required again' was dropped without replacement. Separately, project fact (security.md S1, S3): a crafted Markdown or canvas document can post any bridge message. If the run action is an `arch` bridge action and the confirmation is rendered in the web page, a document could start an operation without the user confirming. The spec does not state that the confirmation must be enforced on the native side and that the command is taken from the operations file, not from the bridge payload.

> A command written by one person will run on another person's machine; the confirmation before every run (DEC-002, REQ-003) is the safeguard

## Possible interpretations

- Accept the risk: uniform confirmation only, no change detection.
- Highlight in the confirmation that the command or working directory differs from the last version run on this machine (needs machine-local state, which REQ-006 currently forbids for the list itself but not for run history).
- Require the confirmation to be a native dialog and the bridge payload to carry only the operation id.

## Resolution

AI: Подтверждение показывается нативным диалогом и принудительно выполняется на нативной стороне; bridge-сообщение несёт только id операции, а команда и рабочий каталог читаются из файла операций. Если команда или каталог отличаются от последней версии, подтверждённой на этой машине (или операция ещё не запускалась здесь), диалог явно это выделяет и показывает прежнюю команду. — see DEC-014.
