## Context

F-003: the spec does not define credentials, required scope, target repository resolution, unauthenticated/no-write behaviour, or rate-limit handling. MarkView already integrates GitHub via the gh CLI (GitHubViews.swift shows gh auth login / gh auth refresh flows).

## Alternatives

1. Reuse gh CLI auth (existing integration)
2. Separate personal access token stored in Keychain
3. GitHub App / OAuth device flow owned by MarkView

## Decision

Sync calls GitHub through the gh CLI using the user's existing gh login; no separate token is stored. The default repository is the project's GitHub origin remote; links that explicitly name owner/repo (URLs, owner/repo#n) target that repository. Before running, Sync checks that gh is installed and authenticated and that the user has write (triage or higher) access to the default repo; if not, the Sync action is disabled/aborted with an actionable message (gh auth login / gh auth refresh) and no changes are made. Per-issue permission, not-found or rate-limit errors are reported as 'failed' with the error in the REQ-004 report; the remaining items continue. On a secondary rate-limit response Sync waits the indicated retry-after once, then reports failure; no other automatic retries.

## Reason

Consistent with the existing GitHub integration and its auth UX, adds no secret storage, and GitHub itself enforces permissions. Pre-flight checks avoid partial runs caused by a missing login; per-issue failure reporting fits the apply-immediately model (DEC-001).

## Consequences

Requires the gh CLI to be installed and logged in; users without write access cannot sync. A new requirement is needed for the pre-flight check and the error mapping, plus acceptance criteria covering the unauthenticated, no-write-access and rate-limited cases. Cross-repo links depend on the user's access to those repos. Sync can fail partway, and the report lists what was and was not applied.
