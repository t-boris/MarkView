## Context



## Alternatives

1. Make the Definition of Done the single source and derive the process from it
2. Synchronise both ways

## Decision

What counts as delivered is decided by the process (integration, checks, delivery event, acceptance), as the Workflow tab already says. The Definition of Done checklist is shown next to it and a disagreement is a warning, never an automatic change. Choosing a flow replaces the states and transitions only: processes that follow the transitions of their type keep their delivery settings, and a new project gets the processes its Definition of Done gave at adoption (the feature process still needs no pull request or checks, the bug process follows the checklist).

## Reason

Two sources of Done that disagree (the checklist requires a pull request and CI, the standard feature process allows direct commits without checks) is what Boris could not see. One authority plus a visible warning removes the surprise without silently rewriting a process.

## Consequences

The warning shows wherever the checklist requires more than the feature process (a pull request and CI are required by the standard checklist, the standard feature process accepts a direct commit without checks). A process with transitions of its own is dropped when a flow is chosen, because its steps name the statuses of the old flow; saving lists the items that followed it.
