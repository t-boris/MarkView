## Context

MarkView's own guided flows for a new feature (intake writes idea or exploring; the specification steps move a feature through draft, review, resolving and ready) are built around the standard stage names. REQ-002 lets a project rename or remove any status, which the spec does not say how to reconcile with those flows.

## Alternatives

1. Give every guided step a role (for example 'being specified') and let the workflow choose which status plays it: a larger model change with no requirement behind it.
2. Forbid removing or renaming the standard specification stages in the editor: contradicts REQ-002, which allows any status to be configured.

## Decision

The lifecycle itself (transitions, completion, reopening, GitHub synchronization, filters, badges, the agent tools) reads lifecycle roles and the project workflow, never status names. The guided specification flows of the app keep writing the standard stage ids (idea, exploring, draft, review, resolving, ready) when they create or advance a feature. If the project's feature workflow no longer has such a status, the status is written but the lifecycle judges it as a status the workflow does not know (never a pass), and the person is told in the Lifecycle section. A project that renames the specification stages therefore changes the statuses by hand or through the agent tools, which read the workflow.

## Reason

Making the guided flows follow arbitrary stage names would need a mapping from each flow step to a role-like concept that no requirement defines; the lifecycle consumers that decide completion and evidence do not depend on those names, which is what REQ-002 and REQ-003 require.

## Consequences

A project that removes a specification stage can still use the guided flows only by keeping or re-adding that stage id. The editor validates roles (not started, active, completed), not stage names, so it does not block such a workflow. A later feature can add steps with roles.
