## Context



## Alternatives

1. Treat evidence that cannot be read as not required.
2. Let an AI continue when only a minor source is unavailable.

## Decision

Every condition returns completed, not completed or unknown, with a reason and the source (the three results the delivery verdict already has). Evidence: start = the hand-off or attached session, or (variant permitting) a person's note recorded in the history; integration path and pull request = the merged pull request or the commit on the default branch, read from git and GitHub, with the changed files telling code from documentation; checks = the workflow runs of the head commit from GitHub; GitHub release = a published release that contains the merged work; confirmed event = a person's confirmation recorded in the history since the item was last reopened; acceptance = the acceptance transition by a person, or by an AI with evidence and every acceptance criterion ticked where the variant allows it. Evidence that is missing, unreadable, stale or ambiguous is unknown and is never a pass: the transition is refused with what is missing and how to supply it. Only a person can make a one-time exception, with a reason; it is recorded with the conditions it bypassed, does not change the workflow, and is not verified completion.

## Reason

REQ-005 requires the specification to define the evidence of each configurable condition and the behaviour when it is unavailable. This restates the existing behaviour of the delivery verdict (DeliveryVerdict, IssueLifecycle) for every condition so that a new condition cannot weaken it.

## Consequences

A project without GitHub can only use variants whose conditions need no GitHub (direct integration, no checks, no release, or a confirmed event); a variant that needs GitHub there is blocked with a clear reason, not skipped.
