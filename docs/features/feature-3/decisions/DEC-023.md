## Context

Custom statuses need meanings that consumers can use to distinguish active, completed, and reopened work. Transition validation alone does not define those meanings.

## Alternatives

1. Keep status names arbitrary and configure completion, start, delivery, and reopening separately.
2. Map each custom status to an existing feature or bug status and inherit its behavior.

## Decision

Assign every status a lifecycle role, such as not started, active, completed, or cancelled. A transition from a completed role to a non-completed role is a reopening. A role alone does not confirm delivery.

## Reason

The selected approach gives custom statuses shared lifecycle semantics while keeping evidence requirements explicit and independent of status roles.

## Consequences

REQ-002 must require a lifecycle role for every status and define how roles affect completion and GitHub synchronization. Existing statuses need default roles. Start and delivery evidence remain explicit transition conditions.
