## Context

DEC-016, DEC-022 and DEC-024 say that a workflow is adopted automatically and that every item gets a rule variant, but not where either is kept or what happens when the stored policy cannot be read.

## Alternatives

1. Store the policy in a tracked file such as docs/workflow.json so it is shared through git (needs a decision on where, and `.dde/` is ignored by git).
2. Store the variant in the front matter of every feature and bug (adoption would rewrite every document and dirty the working tree).
3. Fall back to the standard rules without saying so when the file is damaged.

## Decision

Store the project workflow as one JSON document `.dde/workflow/workflow.json` (schema version, revision, name, feature and bug lifecycles, rule variants, default variant per work-item type) next to the existing lifecycle journal. The variant assignment of each work item is not a separate file: it is a record of the lifecycle journal `.dde/lifecycle/transitions.jsonl` (phase `assignment`: variant, actor, time, reason; the last record of an item wins), so the assignment sits next to the transitions it explains. Every saved change of the workflow raises its revision; transition records name the workflow revision and the variant they were decided under, and keep the status ids they were written with. A person's start note, a person's delivery confirmation and a replacement made when a status was removed are journal records too (phase `evidence`, transition kind `replacement`). A missing file means the project has not adopted a workflow yet: adoption writes the standard workflow (migrated per DEC-022) and records the standard variant of its type for every existing item (DEC-024); an item without any assignment record is judged by the default variant of its type. A file that cannot be read, or has a schema version this app does not know, is never overwritten or silently replaced: the project keeps working under the built-in standard rules, the Workflow editor and `markview_issue_context` say so, and editing is disabled until the file is repaired.

## Reason

The lifecycle journal and the Definition of Done already live in `.dde/`; the same place keeps one convention and needs no change to the Markdown documents (adoption would otherwise rewrite every feature and bug file). Distinguishing missing, damaged and future files avoids hiding an error behind default rules. Sharing the policy through the repository is a separate question and is not part of this version.

## Consequences

The workflow and the journal are local to the project folder on this machine, like the lifecycle history. A project opened on another machine adopts its own standard workflow there. Old transition records stay readable because they keep their status ids; the history never changes when the workflow does. Because assignments are journal records, a variant change and the removal of a variant in use (DEC-021) are visible in the item's history with who made them and why. This replaces the first draft of this decision, which kept assignments in a separate `assignments.jsonl` file.
