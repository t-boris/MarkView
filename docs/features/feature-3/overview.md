# Процессы разработки для каждого проекта

## Idea

Дать каждому проекту настраиваемый процесс разработки: пользователь выбирает готовую комбинацию правил или создаёт свою, а MarkView применяет её к статусам и переходам feature и bug и использует доступную GitHub-синхронизацию.

## Problem

Проекты по-разному организуют ветки, PR, проверки, приёмку и выпуск. Сегодня часть правил выражена инструкциями и Definition of Done, а действующая проверка переходов не задаёт для каждого проекта единый настраиваемый процесс; кроме того, проверка доставки feature и bug различается.

## Scope

Входит: проектные шаблоны и конструктор процесса, собственные статусы и правила переходов feature и bug, соблюдение правил человеком и AI, подтверждение ручного начала, правила доставки и использование доступной GitHub-синхронизации. Вне первоначально подтверждённого объёма: новые интеграции помимо GitHub; конкретный состав автоматических действий ещё требует решения. Подтверждение доставки может основываться на автоматической проверке опубликованного GitHub release или подтверждении человеком другого события доставки.

## Existing behaviour

- В исследовании зафиксированы решения: разрешить проектные статусы с набором по умолчанию; использовать GitHub для синхронизации при наличии поддержки; считать заметку человека достаточным подтверждением ручного начала; разрешить пользователю менять политику. (`docs/research/2026-11-08-sw-dev-per-project.md`)
- У feature и bug уже есть разные фиксированные наборы статусов. Например, feature проходит через implementing и implemented, а bug — через fixing и fixed. (`MarkView/Models/FeatureVocabulary.swift`)
- Центральная политика проверяет переходы и доказательства; принудительный переход доступен только человеку и требует причины. Для доставки различаются выполненное, невыполненное и неизвестное состояние. (`MarkView/Models/IssueLifecycle.swift`)
- Существующий сервис связывает переходы со статусами Markdown и журналом; агент получает текущий статус и доступные следующие шаги. (`MarkView/Models/FeatureStore+Lifecycle.swift`)
- Проектный Definition of Done содержит пункты с режимами require, ask и skip и формирует инструкции для агента. (`MarkView/Models/DefinitionOfDone.swift`)
- Сборщик использует Git и GitHub. Сейчас для feature он отключает требования PR и проверок, а требование релиза вычисляет только для bug; это отличается от общего правила доставки в принятом решении DEC-007. (`MarkView/Models/IssueEvidenceCollector.swift`)
- Существующая синхронизация планирует закрытие или повторное открытие связанной GitHub issue по состоянию локальной работы; расхождения показываются человеку и сами по себе не меняют локальный статус. (`MarkView/Models/IssueGitHubSync.swift`)
- В самом MarkView изменения приложения проходят через PR и выпуск, а изменения только документации — напрямую в main. Это пример необходимости разных правил внутри одного проекта. (`CLAUDE.md`)
