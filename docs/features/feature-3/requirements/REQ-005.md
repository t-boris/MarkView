## Statement

Support project-specific development and delivery rules, with a human-selected rule variant for each new work item and automatic assignment of a standard rule variant to each existing work item when the standard workflow is adopted. Each automatically assigned variant preserves the previous behavior for its work-item type; a person may subsequently select another configured variant, and subsequent transitions use the assigned variant under the current workflow. In the first version, allow each project rule variant for features and bugs to configure conditions for changes reaching the main branch directly or through a pull request, pull request presence and merge, successful checks, and human acceptance. Define the available evidence for each condition and the behavior when evidence is unavailable. Support independently configured delivery requirements and events for features and bugs, automatic verification of a published GitHub release or human confirmation of another delivery event, and a human-selected replacement when deleting a variant in use. Assign every status a lifecycle role, with default roles for existing statuses. Treat a transition from a completed role to a non-completed role as a reopening. A role alone does not confirm delivery; start and delivery evidence remain explicit transition conditions. When the standard workflow is adopted, migrate existing verifiable transition rules into it while preserving existing feature and bug transition behavior. The workflow becomes authoritative for transition conditions; the Definition of Done and project instructions remain guidance for carrying out work and do not change transition conditions when subsequently modified.

## Acceptance Criteria

- [ ] A person selects a configured rule variant for each new work item.
- [x] When the standard workflow is adopted, every existing work item is automatically assigned a standard rule variant that preserves the previous behavior for its work-item type.
- [ ] A person can select another configured rule variant for a work item after its initial assignment.
- [x] A work item's subsequent transitions use its assigned variant under the current workflow.
- [ ] Before deleting a rule variant used by work items, the user must choose a valid replacement for the affected items.
- [ ] After deletion, affected work items use the selected replacement variant for subsequent transitions.
- [x] Each project rule variant can independently configure delivery requirements for features and bugs.
- [x] Each project rule variant can independently configure delivery events for features and bugs.
- [x] Each project rule variant can configure conditions for feature and bug changes reaching the main branch directly or through a pull request.
- [x] Each project rule variant can configure pull request presence and merge conditions for features and bugs.
- [x] Each project rule variant can configure successful check conditions for features and bugs.
- [x] Each project rule variant can configure human acceptance conditions for features and bugs.
- [ ] The specification defines the available evidence for each configurable development condition.
- [ ] The specification defines the behavior when evidence for a configurable development condition is unavailable.
- [x] A workflow can require automatic verification of a published GitHub release as delivery evidence.
- [x] A workflow can require human confirmation of a delivery event other than a published GitHub release.
- [x] Every status has a lifecycle role.
- [x] Existing statuses have default lifecycle roles.
- [x] A transition from a status with a completed role to a status with a non-completed role is treated as a reopening.
- [x] A status's lifecycle role alone does not confirm delivery.
- [x] Start evidence remains an explicit transition condition.
- [x] Delivery evidence remains an explicit transition condition.
- [x] When the standard workflow is adopted, existing verifiable transition rules are migrated into it.
- [x] The migrated standard workflow preserves existing feature and bug transition behavior.
- [x] After the standard workflow is adopted, the workflow is authoritative for transition conditions.
- [x] The Definition of Done and project instructions remain guidance for carrying out work.
- [x] Subsequent changes to the Definition of Done or project instructions do not change transition conditions.
