## Context

Boris described a "double synchronization" between prototype and product. Both sides can change between two syncs; an automatic two-way merge would have to resolve conflicts between a code change and a prototype edit of the same component, and the prototype is only an approximation of the product.

## Alternatives

1. Automatic two-way synchronization that merges both sides.
2. Only code to prototype; prototype changes are described to agents by hand.

## Decision

The two directions are separate actions the person starts: "Sync from code" (code to prototype, REQ-010) and "Hand off to code" (prototype to code, REQ-012). They share one baseline, the state of the code at the last sync (REQ-009). When a component changed on both sides since the baseline, both actions warn about it before they run (REQ-011).

## Reason

Keeps every transfer explicit and reviewable, avoids silent merges between an approximate prototype and real code, and still gives the person the loop they described: change the prototype, hand off, let the code change, sync the affected parts back.

## Consequences

No background watching of files. The baseline is the single reference point for what "changed" means on either side.
