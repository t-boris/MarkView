## Context

Sync from code clears site/ and runs the whole creation build again, so a one-file change costs as much as the first build (tens of assistant runs on a large app). DEC-005 of previews-from-existing-code (point 1) also decided that Studio edits are not carried over: they stay only in the version history. Boris objected to the cost and asked that the state be remembered after a sync and only a changed file or component be synced.

## Alternatives

- Keep the full rebuild and only make it faster.
- Incremental sync that also tries to re-apply Studio edits to rebuilt units by merging them (agent merge).
- Incremental sync that overwrites edits in rebuilt units and keeps them everywhere else (chosen here).

## Decision

Sync compares the current sources with the baseline saved with the latest version and rebuilds only the units (foundation, screens, component pages) whose sources changed or are new; units whose sources were removed are dropped; every other file stays byte-identical, Studio edits included. Rebuilt units overwrite the edits made in them, and the reply lists which. Nothing changed means no run and no new version. This replaces point 1 of DEC-005 of previews-from-existing-code; points 2 and 3 of that decision stay.

## Reason

Boris asked for it on 2026-11-03 and answered "Да" to the question about reopening DEC-005; marked proposed until he confirms that this answer covered point 1 of DEC-005. Rebuilding only what changed is the only way sync stays affordable on a large application.

## Consequences

A sync baseline (hash of each source file, the sources each unit was built from) is saved with every version and restored with it (REQ-009). A prototype saved before this feature has no baseline: its first sync is a full rebuild that writes one. Where the source-to-unit mapping is unknown or a shared input changed, sync falls back to a wider rebuild and says why (REQ-011).
