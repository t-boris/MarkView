## Context

Web and native QA already exist. Boris requested API inference, scenario proposals and backend end-to-end execution in the active 2026-11-11 goal.

## Alternatives

1. Have the assistant choose and send requests at every replay (less reproducible and may repeat mutating requests).
2. Mix browser, native and API steps in a single scenario (outside this goal's requested third type and contrary to the existing one-type-per-scenario choice).

## Decision

Add an api scenario kind beside web and nativeMacOS. Generation reads project routes/tests and attached OpenAPI or API documentation and proposes executable request templates. Each step persists method/path/headers/body, expected statuses, JSON Pointer equality checks and captures. API execution sends each saved request once and evaluates checks directly; it never asks an assistant to invent a passing verdict. Cookies, response history and captured values belong to one actor/service and one branch. API runs retain approval, production confirmations, stop, outcomes, archives and bug filing; report HTTP evidence instead of screenshots or video.

## Reason

The existing graph and driver seam support the third application type while reusable request templates make backend checks reviewable and repeatable.

## Consequences

HTTP(S) requests stay on the configured service origin; redirects are checked as responses. Saved credentials use placeholders and authentication responses can capture secret tokens. API faults require actual service behavior or manual preparation.
