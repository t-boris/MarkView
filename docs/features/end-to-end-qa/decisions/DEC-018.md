## Context

One product can consist of several applications (a user application, an administration application, a partner application) used by several players at once. The first model had one target per environment holding one address.

## Alternatives

1. One scenario per application; flows that cross applications cannot be checked.
2. Keep one application per scenario and describe the others in words.

## Decision

A scenario lists its applications. An environment (local, development, production) maps each application to its location: an address for a web application, an installed application for a native one. Each player belongs to an application, and a step may name its own application. All applications of one scenario are of the same type.

## Reason

Boris described products with three applications and five players, and checks that follow one flow across them.

## Consequences

The generator, the editor, preparation, the run and the material policy work per application. Generation allows at most 6 applications and 10 players. A scenario that is valid for one application stays valid with one application listed.
