## Context

A user-facing application and an administration application are judged by different standards, and a claim that an application is fast needs a measurement.

## Alternatives

1. One review prompt for every page of every application.
2. Let the AI judge speed from screenshots only.

## Decision

Each application has a profile: user-facing (attractive, production-ready, attention-catching), administration (fast, optimal, ready for automation) or custom, with requirement text the user can edit. During the run MarkView measures the time of each step and, for a web application, the page's own load time and the slowest requests (browser Performance API, paths without query strings), and counts the buttons, links and fields that have no identifier, name, test attribute or label. For a native application the step times and the controls without a name come from the accessibility tree. The review of an application gets its requirement text and that evidence, labelled as measured; the AI judges the rest of automation readiness (predictable addresses, actions that can be repeated safely).

## Reason

The profiles express what Boris wants from each kind of application, and measured numbers keep the speed finding honest.

## Consequences

The runner collects timings and counts as facts about the page, not its content: request paths carry no query string or fragment and no value a person typed is read. In a single-page application the request times are cumulative since the document loaded, and the browser keeps only the first 250 entries. The review names the application and the requirement in every finding and bug. The three presets are a starting text, not a fixed list.
