## Context

A user-facing application and an administration application are judged by different standards, and a claim that an application is fast needs a measurement.

## Alternatives

1. One review prompt for every page of every application.
2. Let the AI judge speed from screenshots only.

## Decision

Each application has a profile: user-facing (attractive, production-ready, attention-catching), administration (fast, optimal, ready for automation) or custom, with requirement text the user can edit. During the run MarkView records timings for each step (page load and request durations for web; step durations for native) and signals of automation readiness (stable identifiers, labelled controls, predictable addresses; for native, accessibility identifiers and labels). The review of an application gets its requirement text and that evidence.

## Reason

The profiles express what Boris wants from each kind of application, and measured numbers keep the speed finding honest.

## Consequences

The runner collects timings and readiness signals as page-level facts, not page content. The review names the application and the requirement in every finding and bug. The three presets are a starting text, not a fixed list.
