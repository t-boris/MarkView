## Question

Should QA also check an HTTP/REST service, as a third application type next to web and native macOS: the product's web application, its Mac application and its service, where QA learns how the service works and the main scenarios simply call the matching requests?

## Why it matters

Boris proposed this on 2026-11-10 as a way to develop the feature. A real product often has a web application, a Mac application and a service behind both, and the service is the cheapest place to check the same flow: no screen, no recording, fast, repeatable. It touches Q-009 (answered: one application type per scenario) and DEC-007, because a flow that goes through the service and a screen is a mix of types. The runner already has an `http` action for preparing data, which is a starting point, and the actor driver is a protocol, so a service driver would plug in beside the web and native ones.

## Options

- **A**: Later, as its own scenario type: add an HTTP service type (requests, expected status and body, learned from an OpenAPI description or from the project's code) in a follow-up feature; keep Q-009 and DEC-007 as answered.
- **B**: Now, in this feature: add the HTTP service type before closing it; a scenario still has one type.
- **C**: Now and mixed: a scenario may combine web, native and service steps (reverses Q-009 and DEC-007).
- **D**: No: QA stays on screens.

## Recommended

A: it does not delay closing the web and native work, and it can be built on the finished actor-driver seam instead of being squeezed into it.
