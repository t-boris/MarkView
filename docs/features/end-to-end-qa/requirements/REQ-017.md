## Statement

The system shall support HTTP/REST APIs as a scenario type alongside web and native macOS, proposing executable requests from the project API contract and running saved scenarios with deterministic response checks.

## Acceptance Criteria

- [ ] The new-scenario sheet and scenario editor offer HTTP API, with HTTP(S) base URLs per service and environment.
- [ ] The assistant reads attached OpenAPI/Swagger/API documentation and project routes/tests to propose request methods, paths, headers, bodies, auth and meaningful positive and negative branches; malformed or missing executable requests prevent approval.
- [ ] Requests and response checks are editable and persist with the scenario. Replays send saved requests once without an assistant deciding whether the response passed.
- [ ] Status checks, JSON Pointer equality assertions and captures support create/read/update/delete and authentication flows. Missing captures block execution; mismatches fail the branch; expected error responses pass.
- [ ] Each actor/service has isolated cookies and variables, reset between branches. Saved credentials and captured tokens stay out of response evidence. Requests and redirects cannot escape the selected service origin.
- [ ] The existing approval, production confirmation, stop, per-branch outcomes, archive and bug filing remain available. API reports contain response evidence and timings, with no video or screen review controls.
- [ ] A live loopback fixture verifies auth, CRUD, negative cases, failure/block/interruption, replay, isolation and persistence; web/native regression checks and app builds pass.
