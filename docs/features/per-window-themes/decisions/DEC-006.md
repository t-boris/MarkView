## Context

Native colours come from the static VSDark palette (about 1,470 references in about 50 views) that reads NSApp.effectiveAppearance, so it cannot differ between windows. One ThemeManager serves all windows and every window is forced to a dark appearance. The editor, discussion and terminal web pages each carry their own light and dark palettes selected by data-theme or a root class. The specification requires independent themes per window on all of these surfaces. This is the implementer's choice of mechanism; the specification does not prescribe it.

## Alternatives

1. Keep VSDark static and drive it from a global current-window value (cannot be correct while two windows with different themes are drawn).
2. Encode presets as custom NSAppearance names (not possible without an asset catalogue; the system only provides aqua and dark variants).
3. Send every colour from Swift to the web pages as CSS variables (one table, but ties the web token set to Swift and needs a Swift change for each new web token).

## Decision

Each workspace window owns a WindowTheme (selected theme plus per-theme accent overrides). It resolves a ThemePalette that views read from the SwiftUI environment instead of the static VSDark, sets that window's NSWindow.appearance (dark, light, or none for System) and sends the theme id and effective accent to the web pages in that window. One shared web file defines the token tables of the six appearances (Classic Dark, Classic Light, Darcula-inspired, Midnight, Graphite, Paper) and is used by the editor, discussion and terminal pages. The model, palettes, contrast rules, migration and persistence live in a Foundation-only file with standalone checks. The old static palette, the single shared ThemeManager and the per-page light/dark tables are removed, not kept as fallbacks.

## Reason

The environment is the standard SwiftUI way to scope a value to one window's view tree and matches the existing appFontScale pattern; a static or application-wide palette cannot satisfy window independence. The mechanical replacement of VSDark keeps the view code otherwise unchanged.

## Consequences

About 50 view files change mechanically (VSDark.x becomes palette.x with an environment property per view). Models that returned VSDark colours must return semantic values that views map through the palette. Swift and the web token file both hold the base colours of each theme; a check compares them so they cannot drift. Existing menu item Toggle Theme and its shortcut open the picker (DEC-001).
