## Context

Boris (2026-11-05, mid-turn): add the ability to add an image to a node, along with the icon. The existing Image kind (REQ-012) replaces the text of the card with a picture whose address is typed by hand. Boris chose a thumbnail beside the icon, with the icon staying.

## Alternatives

1. Embed the picture as a data: URI in the map file (huge lines, slow parse, diff noise)
2. Only an address typed by hand (what the Image kind does today)
3. Allow SVG (can carry scripts)
4. Replace the icon with the picture (Boris wanted both)

## Decision

A node gets an optional `image` property (`- image: images/<name>.<ext>`): a relative path without `..` or an https address. The page sends a chosen, dropped or pasted file as Base64 (`attachImage {id, name, data}`); `ResearchMapImages` checks the bytes (PNG, JPEG, GIF, WebP, at most 6 MB; SVG and HTML are refused), writes it off the main thread into `images/` beside the map file under a safe unique name, and `ResearchMap.update(image:)` sets it through the single writer. The card shows a 30 px thumbnail between the icon and the title.

## Reason

A file in the project keeps the map self-contained and diff-able, a path is one short line in the map file, and checking the bytes (not the name) with a fixed list of kinds keeps scripts out. Writing off the main thread follows the project rules; the map is still changed only by its single writer.

## Consequences

The old picture file stays in images/ when it is replaced or removed (it may be used elsewhere). The report, the PDF and the translation do not use the picture yet; the translation keeps the line. A hand-written https address makes the page load it when the map opens, as the Image kind already does.
