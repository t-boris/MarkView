## Context

DEC-003 stores every new research map as a human-readable Markdown file and requires the specification to define how hierarchy, properties, logical connections, evidence and layout settings are represented, and how the map handles edits made in an ordinary text editor. The prototype assumption (SRC-002 SPEC.md, section 7) is a single file with nested lists for the hierarchy and sections with stable node ids for the details; the overview says the internal format is left to the implementation.

## Alternatives

1. A structured JSON or YAML file for the map with a Markdown export (rejected in F-001/DEC-003)
2. One heading level per tree depth, so the hierarchy is the heading outline (rejected: deep maps exceed six heading levels and descriptions would collide with headings)

## Decision

One file per map at docs/research/<date>-<slug>.md (the path the New Research sheet already proposes). Front matter: type: research-map, id (file name without extension), title (mirrors the root node), question, created, status (researching | complete | incomplete), incomplete (the reason, only while status is incomplete), targets, attachments, web_queries (every web search query the AI sent, in order, without duplicates). Body, in this order: "# <title>"; "## Question" (the question text); "## Map" (nested Markdown list, two spaces per level, one item per node, written "[Title](#id)"; the first top-level item is the root); "## Connections" (one item per logical connection, "[A](#id) ↔ [B](#id)", undirected, never the same pair twice in either order); "## Nodes" (one "### <Title> {#id}" section per node). A node section starts with an optional property list, "- tags: a, b", "- color: #rrggbb", "- layout: <preset id>", "- position: x, y" (only when the node was moved by hand); then the description as Markdown; then an optional "#### Evidence" heading followed by one item per finding, "- [Project fact] text — `path:line`", "- [External fact] text — <https://url>", "- [AI inference] text", "- [Open assumption] text" (the four labels of the existing research; the source is what follows the last " — "). Node ids are n1, n2, … and never change; a new node gets the highest number plus one. Sections the app does not know are kept verbatim after "## Nodes". The title in the "## Map" list is the node's title; the heading text of its section is rewritten from it. Tolerance for edits outside the map: a list item without "(#id)" becomes a new node with a fresh id; a "###" heading without a known "{#id}" belongs to the description of the node above it; a section whose id is not in the list is dropped; a connection naming an unknown id, the same node twice or a repeated pair is dropped; a second top-level item becomes a child of the root; unknown property lines are ignored. The app rewrites the file in this canonical form the next time the map is changed from the map view. A file that has no "## Map" list or an unreadable front matter is not a map: the tab stays in the Markdown source view and says why. While a map tab is open the app watches the file (the existing two-second check), so an edit saved in another editor appears in the map when the tab has no unsaved changes; edits made in the tab's own Source view appear when the user returns to the map.

## Reason

Nested lists show the hierarchy in any Markdown viewer, per-node sections keep descriptions and evidence next to their title, and links to #id anchors make the outline navigable in a rendered preview. Ids that never change keep connections and layout settings valid when titles are edited by hand. Reusing the existing research labels keeps the verification rules of the current report.

## Consequences

A Swift module parses and writes this format and is the only implementation of it; the map view receives parsed data and sends operations. Tests parse and rewrite fixtures, including hand-edited ones. The format is versioned by the front matter type; a later change adds a version key rather than reusing keys.
