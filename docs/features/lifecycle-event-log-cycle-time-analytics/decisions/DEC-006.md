## Context

Q-002 asked which fixed lifecycle stage list is canonical. DEC-003 had fixed a minimal list; the product owner chose the extended list to expose bottlenecks in spec, review and CI steps.

## Alternatives

1. Minimal: idea created → implementation started/finished → merged → verified
2. Extended: minimal + spec ready, questions resolved, review, CI passed
3. Open: arbitrary configurable event types

## Decision

Use the fixed extended list in this order: idea created → questions resolved → spec ready → implementation started → implementation finished → review done → CI passed → merged to main → verified. Idea created, questions resolved and spec ready are captured automatically in MarkView; the other stages are marked manually (per DEC-002). Event types outside this list are not supported. This supersedes DEC-003.

## Reason

Chosen by the product owner: the extended list reveals process bottlenecks (clarification, review, CI) while a fixed list keeps durations comparable across features and models.

## Consequences

More manual marking for review and CI passed; the per-step summary table gains more rows. Stage order is an AI inference to be confirmed in review. Steps may be skipped or repeated in practice; durations are computed only between recorded events.
