## Context

The overview has an acceptance criterion that an operation needing interactive input can receive it. DEC-001 and REQ-001 run operations as a dedicated subprocess without a terminal tab, and REQ-002 defined the output panel as display-only. An operation that asks for a password, a y/n confirmation or a 2FA code would hang until cancelled. AI inference (not a verified fact): deployment commands ask for input often enough that this is not a rare case.

## Alternatives

1. A: The output panel accepts input; the user types into it and the text is passed to the process.
2. B: Input is not supported; the overview criterion is dropped and a command waiting for input fails or is cancelled by the user.
3. C: Input is not supported, but the panel offers an 'Open in terminal' action that pastes the same command into an embedded terminal tab.

## Decision

Option A: while an operation is running, the user can type into its output panel and the typed text is delivered to the process as its input. Input that the process asks for without echo (passwords, codes) is not displayed and is not kept in the retained output. Execution remains a dedicated subprocess as decided in DEC-001; no terminal tab is opened.

## Reason

The user chose option A. It keeps a single execution path with operation state and cancel, satisfies the overview's acceptance criterion, and makes operations with password, confirmation and 2FA prompts usable from the buttons.

## Consequences

REQ-001 and REQ-002 are refined. The output panel grows in scope: it must accept input and hide secret input. AI inference: many tools prompt only when they are attached to a terminal, so the subprocess has to look like a terminal session to the command; how this is done is left to the implementer. The system does not detect that a process is waiting for input; the user sees the prompt in the output and answers it. Option C's second execution path (embedded terminal tab) is not built.
