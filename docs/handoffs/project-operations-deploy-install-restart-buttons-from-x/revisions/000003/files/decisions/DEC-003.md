## Context

The idea requires discovery to investigate unfamiliar tooling and procedures that live in another local folder or project (local folders first, then the web). The current deployment mapping works only from inlined config files and reads nothing itself. Reading folders outside the project and sending web queries affect privacy and security, so the permission boundary had to be chosen by the product owner.

## Alternatives

1. A: Fully automatic - discovery reads folders outside the project root and searches the web on its own, then reports what it found and where.
2. B: Automatic inside the project root; each folder outside the project and any web access only after user confirmation.
3. C: Automatic inside the project root; external folders are named by the user in advance; web access after confirmation.
4. D: Project root only and no web in the first version; unknown tooling is reported as not determined.

## Decision

Option A: discovery runs fully automatically. It may read local folders outside the project root and search the web without a separate permission prompt, and afterwards reports what it found and where each command came from.

## Reason

Chosen by the user. It gives the least friction, completes discovery in a single pass and best covers the stated scenario of unfamiliar tooling and install procedures located in another project.

## Consequences

Discovery is read-only and never executes commands; execution stays gated by the confirmation before every run (DEC-002). Files outside the project are read without the user being asked, and project-related terms may appear in web search queries; this risk is accepted. To compensate, every discovered operation must carry its provenance (local paths read, web sources used) and confidence, visible to the user. Discovery needs a new AI pass with read and web access, because the existing deployment mapping prompt forbids reading.
