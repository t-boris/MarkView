## Context

F-019: project fact: GitHub Actions workflow dispatch already exists in MarkView behind the opt-in GitHub setting, and .github/workflows/* is among the scanned config files. No decision says whether discovery proposes such deploys. External fact: `gh workflow run` exits once the workflow run is queued, so exit code 0 means the run was requested, not that the deploy finished. Remote monitoring is out of scope.

## Alternatives

1. A. Discover workflow-dispatch deploys as ordinary operations; 'succeeded' means exit code 0.
2. B. Exclude workflow-dispatch deploys from discovery in the first version.
3. C. Discover them as operations with a 'remote trigger' flag; exit code 0 is reported as 'dispatched', with a statement that the remote run is not tracked.
4. D. Route them to the existing workflow dispatch feature and show them only when the GitHub setting is enabled.

## Decision

Option C. (1) Discovery proposes an operation for each workflow with a workflow_dispatch trigger that it classifies as operational; the command is a `gh workflow run` invocation and the source is the workflow file. (2) Such an operation carries a boolean attribute marking it as a remote trigger. Discovery sets it for workflow-dispatch operations; the user can set or clear it on any operation when editing (DEC-004). (3) For a remote-trigger operation, exit code 0 is shown as 'dispatched' with the text 'remote run is not tracked' in the operations list, on the Deploy buttons, in the output panel and in the notification. A non-zero exit code is 'failed' as usual. (4) The run confirmation states that the command only starts a remote run and MarkView will not report its result. (5) The operation is an ordinary subprocess (DEC-001, DEC-013) and does not depend on the opt-in GitHub setting; it uses the `gh` installation and authentication of the user's shell. `gh` being installed and authenticated is listed as a prerequisite (DEC-023). (6) Workflow inputs with a fixed set of choices that represent environments produce one operation per value; other required inputs without a default are listed in prerequisites and left for the user to add by editing the command.

## Reason

For many projects workflow dispatch is the only deploy path, so excluding it would leave the Deploy button missing exactly where users expect it. Reporting 'succeeded' would be misleading for a production deploy that may still fail remotely. A distinct outcome label is a small addition and keeps remote monitoring out of scope. The GitHub setting governs MarkView's own GitHub integration; here the user runs an explicit, reviewed command after confirmation, the same as any other CLI tool, so tying it to the setting would add a dependency without a safety gain.

## Consequences

The operations file schema (DEC-017) gains one optional boolean attribute, and the state model gains the display outcome 'dispatched' for remote-trigger operations; REQ-002, REQ-012 and REQ-013 need matching criteria. The same flag serves other asynchronous triggers (for example a command that only starts a remote pipeline). Two paths to dispatch a workflow will exist in the product (the existing dispatch feature and operations); unifying them is left out of the first version. Open assumption: the rule in (6) for mapping workflow inputs to environments is an inference and needs validation on real workflows.
