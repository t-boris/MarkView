## Finding

DEC-007 states the subprocess 'has to look like a terminal session to the command; how this is done is left to the implementer'. This leaves open behaviour that is visible to the user: (1) handling of ANSI colour, cursor movement and carriage-return progress bars, which most deploy tools emit when attached to a terminal; (2) terminal size and resize; (3) full-screen or editor-style programs; (4) how the user sends end-of-input or control keys, and whether input is sent per key or per line; (5) how 'input without echo' is detected; (6) the amount of output retained and what happens when it is exceeded (the overview records a known risk of silent truncation on large terminal writes); (7) whether output is kept in memory only or written to disk, given that deploy output may contain secrets and security.md forbids logging credentials. Project fact: an embedded PTY terminal with a terminal web view already exists; whether the panel may reuse that component (while remaining a separate execution path per DEC-001) is not stated.

> When the process requests input without echo, the typed characters are not displayed in the panel and do not appear in the output retained after the process ends.

## Possible interpretations

- The panel is a full terminal emulator (reuses the existing terminal view component) bound to the operation's process.
- The panel is a line-oriented log with a single input field; escape sequences are stripped, full-screen programs are unsupported.

## Resolution

AI: Панель вывода — полноценный эмулятор терминала на существующем компоненте (xterm.js поверх PTY), привязанный к отдельному процессу операции, а не к вкладке терминала. Вывод хранится только в памяти с ограниченным буфером прокрутки и явной пометкой об усечении, на диск не записывается. — see DEC-019.
