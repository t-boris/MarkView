## Context

REQ-002 only says that cancel terminates the process and its children and shows the operation as cancelled. The first signal, the grace period, the state during termination, the handling of detached children and the final state when the process exits by itself after cancel was requested are undefined. AI inference: tools that hold remote locks (e.g. terraform) need time to clean up after an interrupt, so an immediate force-kill can leave locks or partial changes behind. Operations run on a pseudo-terminal (DEC-013, proposed).

## Alternatives

1. Interrupt, fixed grace period, then force-kill the process group; state is 'cancelled' regardless of exit code.
2. Force-kill immediately.
3. State follows the real outcome: 'succeeded' if the process finished before the signal took effect.
4. Interrupt only, never force-kill automatically; the user must force-stop manually.

## Decision

(1) Cancel asks for a single confirmation that warns that the target environment may be left partially changed; the warning is the same for every operation kind. (2) On confirmation the system sends SIGINT to the operation's process group and the state becomes 'cancelling'. (3) If the process is still alive after 30 seconds, the system sends SIGTERM to the process group, and after 5 more seconds SIGKILL. The panel shows the remaining grace time. (4) While the state is 'cancelling', a 'Force stop' control is available that sends SIGKILL to the process group immediately. (5) The start control stays unavailable during 'cancelling' (REQ-009). (6) Final state: if the process was still alive when cancel was confirmed, the final state is 'cancelled' whatever the exit code; the panel additionally shows the exit code or terminating signal and whether the stop was forced. If the process had already exited before cancel was confirmed, the state follows the real outcome (succeeded / failed). (7) Child processes that detached into their own session are not tracked; closing the pseudo-terminal is the only measure applied to them, and this is documented as a known limitation.

## Reason

A graceful interrupt first protects tools that must release locks; automatic escalation keeps the promise of REQ-002 that cancel actually terminates the process; 'cancelled regardless of exit code' gives one deterministic, testable rule and avoids showing 'succeeded' for a run the user interrupted.

## Consequences

A new transient state 'cancelling' must be added to REQ-002, REQ-009, REQ-012 and the panel list. REQ-013 notifications fire on the final state only, not on 'cancelling'. A tool that needs more than 35 seconds to clean up will be force-killed; the grace time is a fixed value in the first version. Open assumption: 30 s / 5 s are product choices, not measured values, and may be tuned. Detached children may survive a cancel.
