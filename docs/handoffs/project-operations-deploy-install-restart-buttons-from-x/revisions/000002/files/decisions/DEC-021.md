## Context

No requirement covers running operations on app quit, window close, project close or crash. REQ-002 and REQ-012 keep the final state visible with no time limit. DEC-019 (proposed) keeps output in memory only; DEC-014 (proposed) already introduces a machine-local run history. REQ-009 forbids a duplicate run but does not say how that works with several windows or several app instances.

## Alternatives

1. Quit or close asks for confirmation and terminates all running operations.
2. Operations keep running detached; after restart their state is unknown.
3. Last-run state is in memory only and is lost on restart.
4. Terminate running operations silently on quit without confirmation.

## Decision

(1) When the user quits MarkView, closes the project window or closes the project while at least one of its operations is running or cancelling, the system shows a confirmation that lists those operations (label, environment) and offers 'Stop operations and continue' and 'Keep working'. (2) On 'Stop operations and continue' every listed operation is cancelled with the sequence of the cancel decision (F-009) without a further per-operation confirmation; the quit or close completes when all processes have ended. (3) Operations never continue to run after their project window is closed or the app has quit. (4) For every run the system records in machine-local state: operation id, label, environment, command, start time, end time, final state and exit code. The record is written at start with state 'running' and updated at the end. (5) After an app restart the operations list and Deploy buttons show the last-run state with its end time; the output is not available and the panel states that output is not kept across restarts. (6) A record still marked 'running' at app launch is shown as 'interrupted' with the text that the outcome is unknown; the operation can be started again. (7) The registry of running operations is one per app process and is keyed by canonical project root path plus operation id, so the no-duplicate rule and the displayed state are the same in every window that shows the project. (8) No locking is provided between different MarkView instances or different machines; this is a documented limitation.

## Reason

A deploy that silently continues or silently dies is the worst outcome for the user; a confirmation plus graceful stop is predictable and needs no re-attachment mechanism. Keeping only the run summary locally satisfies REQ-002 and REQ-012 without persisting output that may contain secrets.

## Consequences

A new last-run state 'interrupted' is added; it is never a live state. Run history is not shared with the team and not stored in the operations file. Quit may take up to the cancel grace time. After a crash the child process may have been ended by the closing pseudo-terminal or may still run; MarkView does not detect or re-attach it (AI inference about PTY behaviour, to be verified in implementation). REQ-001, REQ-002 and REQ-012 need added criteria; a new requirement for quit/close is needed.
