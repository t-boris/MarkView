## Context

REQ-006 and REQ-007 depend on an undefined file. Project facts: `.dde/` is listed in .gitignore (line 35), so a file there cannot be shared as DEC-005 requires; the codebase has no YAML parser dependency (no Yams usage found). The file must be hand-editable, mergeable and must identify operations across re-discovery runs.

## Alternatives

1. A: YAML or JSON file under .dde/
2. B: A file under docs/
3. C: A JSON file in a dedicated committed folder, .markview/operations.json
4. D: Same as C but YAML, adding a parser dependency

## Decision

Option C. (1) Path: `<project root>/.markview/operations.json`, UTF-8, pretty-printed with a stable key order and one operation per array element, sorted by id, to keep diffs and merges small. (2) Schema: top level `{ "version": 1, "operations": [...] }`. Each operation: `id` (lowercase slug, unique), `label`, `kind` (deploy|install|build|clean|restart|other), `environment` (string or null), `target` (string or null), `nodes` (array of deployment node ids), `command`, `cwd`, `origin` (discovered|user), `discovered` (object or null: the `command` and `cwd` last proposed by discovery), `deleted` (boolean), `confidence`, `prerequisites`, `provenance`. (3) User edit detection: an operation is user-edited when `origin` is `user` or when `command`/`cwd` differ from `discovered.command`/`discovered.cwd`; therefore a hand edit of `command` in the file is recognised without any extra marker. (4) Deletion: deleting a discovered operation sets `deleted: true` (tombstone, hidden in the UI, never re-proposed); deleting a user-added operation removes the entry. (5) Identity across re-discovery: discovery receives the existing list and must reuse existing ids; a proposal is matched first by id, then by the tuple (kind, environment, target), then by identical command and cwd; only unmatched proposals create new entries, with an id derived from kind, environment and target. (6) Re-discovery and user-edited operations: `command` and `cwd` stay unchanged, `discovered` is updated, and the UI shows that discovery suggests a different command, with an action to adopt it. This closes the open assumption in DEC-004. (7) Provenance: stored in the file; paths inside the project are project-relative; paths outside are written relative to the project root when within two parent levels, otherwise with the home directory replaced by `~`; absolute paths containing a user name are never written. (8) External changes: the file is watched and reloaded on change; the application writes atomically and, if the file changed on disk since it was loaded, reloads and reapplies the single UI change instead of overwriting. (9) Invalid file, including version-control conflict markers: error naming the file, no overwrite (REQ-006), operations and Deploy buttons are unavailable until fixed. (10) Versioning: a file with a higher `version` than supported is opened read-only with a message; unknown fields are preserved on write.

## Reason

.dde/ is ignored by version control, which rules out option A. docs/ mixes executable configuration into documentation. JSON needs no new dependency and is already hand-editable; the cost is less convenient multi-line commands, which are rare because complex procedures belong in scripts. Keeping the last discovered values next to the current ones makes user-edit detection work for hand edits and version-control changes without hidden local state, as REQ-006 demands.

## Consequences

REQ-006, REQ-007 and REQ-005 must be amended with the path, schema, tombstones, matching rules and provenance path form. JSON has no comments; a `note` field may be added later if users ask. Tombstones accumulate in the file; removing one by hand makes the operation eligible for re-discovery. The fields `target` and `nodes` are defined by the F-007 decision and DEC-009. Working directory portability (F-014) and confidence values (F-012) remain to be specified within this schema. Choosing YAML later would be a schema version change.
